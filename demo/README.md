# 双选会会前规划 · 架构说明

> 版本 3.1 · 2026-11-17
> 本文写**整体架构、交接契约、以及哪些不做主**。契约部分是人工对齐过的，改要全组同意；实现细节由各分组自己定。

---

## 0. 要解决的问题

一场双选会能给学生多少时间？两所学校给出两种答案，时长都是三个半小时。

- 南大秋招分三场，鼓楼场 118 家：12600 秒 ÷ 118 ≈ **107 秒 / 家**
- 东南秋招挤在一场，约 485 家：12600 秒 ÷ 485 ≈ **26 秒 / 家**

家数差四倍，每家分到的时间也差四倍。但结论一样：

> **学生只够做一个动作——决定停不停。**

而会前能拿到的公开信息，往往只有一张企业名单，没有任何依据去分配这点时间。

我们做的是**会前规划**：把名单变成一张有依据的优先级排序，告诉学生先走哪几家、哪些可以不去。

不做：简历匹配、资格判定、岗位库、展位导航、现场实时调度。

## 1. 架构

三端一条链，靠文件交接，谁都不用等谁跑完才能开工。

```
企业名单 ─┐
          ├→ ① 用户端 ─→ 用户画像 ─┐
学生 ─────┘                          ├→ ③ 匹配端 ─→ 排序结果 ─→ ④ 页面
                    └→ 企业名单 ─→ ② 企业端 ─→ 企业画像 ─┘
```

| 端 | 输入 | 输出 |
|---|---|---|
| ① 用户端 | 学生答题（可选简历） | 用户画像、企业名单 |
| ② 企业端 | 企业名单 | 企业画像 |
| ③ 匹配端 | 用户画像 + 企业画像 | 排序结果 |
| ④ 页面 | 排序结果 | 能演示的页面 |

## 2. 交接契约

**这一节是对齐过的，字段名一个字母都不许单方改。要改，全组通知，当天跟上。**

### 2.1 企业画像

对齐《企业画像采集端 v1.1》的 9 个采集字段，另加 5 个技术字段。

| 字段 | 含义 | 要求 |
|---|---|---|
| `id` | 企业编号 | 必填，稳定生成 |
| `name` | 企业名称 | 必采 |
| `nature` | 企业类型 | 必采，枚举 |
| `city` | 所在城市 | 必采，单值 |
| `industry` | 所属行业 | 必采，枚举 |
| `jobs[]` | 招聘岗位 | 必采，无岗位写 `[]` |
| `jobSource` | 证据等级 | 必填，枚举 |
| `jobEvidence` | 关键原文 | 非「未知」时必填 |
| `source` | 来源 | 必填 |
| `date` | 采集日期 | `YYYY-MM-DD` 或「未知」 |

`jobs[]` 每项：

| 字段 | 含义 | 要求 |
|---|---|---|
| `title` | 岗位名称 | 必填 |
| `requirements` | 岗位要求 | 必采，查不到写「未知」 |
| `headcount` | 招聘人数 | 非负整数或「未知」 |
| `urgency` | 紧急程度 | 枚举 |
| `group` | 所在组别 | 有则记录，无则「未知」 |
| `salary` | 薪资范畴 | 原文照抄，保留口径 |

### 2.2 用户画像

对齐《用户画像采集端 v1.1》，**不含姓名、手机、邮箱**。

`fair_id` `event_date` `target_stage` `stage_detail` `region` `home_city` `direction_interest` `target_company_types` `values` `timeline` `major` `degree`

`values` 是对象：`salary stability growth autonomy impact balance`，六个整数合计 100。

### 2.3 排序结果

`id` `tier` `score` `distanceKm` `nearestCity` `reasons` `gaps`

### 2.4 枚举

| 字段 | 取值 |
|---|---|
| `nature` | 央企 / 国企 / 民企 / 外企 / 合资 / 事业单位 |
| `industry` | 制造 / 医药 / IT / 金融 / 建筑 / 能源 / 消费 / 物流 / 教育 / 政府事业 / 其他 |
| `urgency` | 高 / 中 / 低 / 未知 |
| `jobSource` | 校招公告 / 社招信息 / 主营业务推测 / 未知 |
| `tier` | 优先去 / 可以看 / 建议放弃 |

### 2.5 缺失值

查不到一律写字符串 `"未知"`。不许 `null`、不许空串、不许省略 key。

### 2.6 已知未对齐（写在这里，别等人踩）

| 项 | 文档写的 | 现行实现 | 处理 |
|---|---|---|---|
| 企业端输入文件名 | `companies.csv` | `company_names.json`（JSON 数组） | **以实现为准**，待统一 |
| 企业端输入形式 | 只收名单文件 | 第三版另加：名单导入（联网补全档案）+ 岗位上传框（隐藏台账 `job_uploads.json`，页面不回显库内清单） | 契约字段不变，输入形式以实现为准 |
| `distanceKm` / `nearestCity` | 在结果对象里 | 匹配端尚未落地 | 待匹配端确认 |
| `values` 六维 | 全部保留 | 只有薪酬、稳定能对上企业数据 | 其余权重挂起，不参与打分 |

## 3. 我们定什么，不定什么

**中央只定接口，实现全部下放。**

| 我们定 | 各分组自己定 |
|---|---|
| 第 2 节的全部契约 | 数据怎么采、用什么手段 |
| 交接顺序与文件位置 | 语言、库、目录结构 |
| 离线可演示 | 打分权重、分档阈值 |
| 查不到写「未知」 | 页面长什么样、测试写几条 |

### 有争议时以谁为准

**契约不一致，找队长；实现细节不一致，以该分组自己的文档为准。**

各分组在自己目录下维护 `README`，那是实现的唯一权威。本文只承诺：**谁交什么、交到哪、字段叫什么。**

---

## 4. 三条不能让的

**① 交接只走文件**
各端不许互相 import 代码、不许直接调对方函数。只认落盘的文件。

**② 断网可演示**
数据采集可以联网，**演示那一刻必须能离网跑**。外部查询结果先落成文件。

**③ 查不到写「未知」，不许编**
宁可一条数据没有，不要一条看着像的。错误的数据比没有数据更糟——学生会信。

## 5. 现在的状态

各端进度见各自目录下的 `README`，本文不重复。

第三版（2026-11-16 起）三端已全部落地并可演示：

- **采集端**：画像问答 + 岗位推荐（大模型联网搜索接地，岗名来自真实校招公告，职能方向级）
- **企业端**：名单导入（联网补全企业档案）+ 岗位上传框（页面不渲染库内清单，上传进隐藏台账）
- **匹配端**：独立排行页，真实命中 / 语义命中 / 推断命中三档，画像×主营复核贯穿（按意向对各算各的方向集）；无方向的管培生/储备干部不算命中，纯大类岗企业后置到队尾
- 页面为单文件构建产物（`demo/fair.html` / `match.html` / `enterprises.html`），离线可演示
