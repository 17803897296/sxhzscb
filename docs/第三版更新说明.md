# 第三版更新了什么

第一，代码整体做了重构，把五处屎山风险点都改了：LLM 调用合并成一份、前端 JS 从 Python 里抽出来、无头渲染改成复用一个浏览器、抓取工具去重、736 行的 build 拆成 443 行加 11 个小函数。

第二，采集端的岗位推荐修正了，之前经常残留计算机和管理类岗位，现在按「专业和经历匹配 → 专业匹配 → 不完全匹配但有门槛 → 专业能去但别人也能去 → 几乎无关」五层逐层放宽，推的都是专业相关能去的。

第三，匹配段的大模型推断换了路线，以前把学生意向塞给模型问「接不接得住」会编出搜不到的岗位名，现在先只看企业主营建岗位画像、比对交给本地代码做。

第四，命中/推断算法做了一串修正：按职能类判定取代凭专业课程推断、复核从二分类改成三态弃权、补行业简称同义词表、幻觉岗位名脱敏、校招公告没有就是没有、现场核实回流改结论。

第五，数据库扩到 14 张表，画像、现场反馈、测试记录都落库，提交画像即生效并后台重算，活库不入库、仓库只放只读种子。

第六，采集流程收口成一条命令，无头渲染从每次开浏览器改成多标签复用（8 页 47→21 秒），外部档案按逐字同名并入，写库只有一处且是合并不是覆盖。

第七，界面改成四端工作台（采集端 / 企业端 / 匹配端 / 测试端），按进度点亮徽标，尽可能美观。

第八，验收：虚拟自动化画像跑完整链路 45 秒，49 家企业 / 357 岗，跨专业残留为 0，四端 HTTP 200、58 个单测 OK，测完数据逐字节还原。

第九，按三套虚拟画像追踪判断路径后，又修了五处常识问题：方向不交叉的企业顺延到队尾不再占前排、工商信息页不再当真实招聘公告、家具厂的结构工程师不再被建筑学生当同名命中、复核弃权的相邻岗位改成现场问一句、职级和文案描述对齐。

第十，再扩到九套画像（计算机/财会/材料/文科/机械/空意向）深测后补了三处：没填意向的不再拿默认意向判「明确命中」、职级高的岗位不再误称「不同职能」、意向里混进空值不再把重算打崩导致页面 500。

第十一，校招来源核实重建岗位库：按岗位真实来源域名重判 145 家，82 家误标 web/未知的其实是校招、纠正为 90 家校招来源；同一企业多渠道岗位合并、只留带 URL 的真岗，删掉 279 条大模型推断补全的假岗。

第十二（2026-11-16～17 迭代，见《第三版技术细节》补记），六件事：

1. **企业端改成岗位上传框，数据库依然隐藏**——原来那页把库内 145 家企业全量渲染（200KB 内嵌数据），现在换成对话框式上传页：粘贴岗位信息/链接或传附件，提交进隐藏台账（`/api/jobs-upload`，页面不回显任何库内清单）；门户门禁文案同步，空提交服务端拒收。
2. **岗位推荐改成联网推荐**——之前模型靠「通用认知」想岗位名，会造词（招聘网站搜不到的职能描述）也会混进与专业关系不大的岗。现在先调 DeepSeek 独立 Search API 搜真实校招公告（标题+摘要+来源，证据缓存 6 小时），模型只准从证据里提岗位名，代码再落地校验：输出岗位名在证据原文里找不到的一律丢掉，「计算机类岗位」这类公告类别标签也拦；页面上联网模式会标「（联网搜索 · 真实校招口径）」。搜索失败自动降级纯模型口径，再降级规则兜底。
3. **推荐池与岗位库彻底解耦**——采集端推荐不再读 careersafari.db（库内岗位含大模型推断岗，会带偏学生自主选择、给匹配端喂答案形成循环污染），候选只依据专业+经历。
4. **画像×主营复检层**——命中判定不再只看「岗位名 ↔ 意向岗位」的字面：全通用意向（管培生/储备干部）× 字面同名岗位要过「企业主营是否容纳专业方向」这道闸（金融公司的管培生不再匹配物流专业选的管培生）；推断命中必须主营出现方向强词，主营为空不推断；被拦的转现场待问。前端换画像重算路径镜像同一规则。
5. **命中治理三连**——泛意向（研发工程师）×带方向岗位（软件工程师）不再硬命中转现场问；轮岗泛岗（管培生/培训生/储备干部）即使业务对口也只现场问；推断命中带箭头标记进报告，橙色标「推断命中，待现场核实」。
6. **未知字段保护与榜单恢复**——重采不再把旧库已知值冲成「未知」（六字段保护闸+旧库回填 26 家）；丢失的排名档案从交接包恢复（52 家有档位），门户补回「测试记录」入口。

注：通用岗位的方向推断已入库（69 条，按企业主营本地推、不用大模型），主营业务补全 144/145 家；排名档案那份文件缺失，所以当前报告里排名档位是 0。

还有一个已知问题留待下版改进：本科学生投博士岗会被判「明确命中」，学历门槛目前没参与判定，这次没动。

详细技术说明见《第三版技术细节》；踩过的坑与改动纪律见《改动守则》。

第十三（2026-11-17 demo 试用反馈，两件事）：

1. **推荐岗放宽到职能方向级 + 跨专业再拦一道**——试用反馈推荐岗太细（「京东新锐之星」这类企业项目名学生对不上），且仍有非本专业岗位混入。联网提示词改为「岗位名给职能方向级的通用叫法」：企业专名 / 项目名 / 地域 / 年份一律归一掉（「京东2026新锐之星（物流方向）」→「物流管培生」）；代码新增三道拦截：项目名黑名单（新锐之星 / 青苗 / 菁英 / 训练营…）、跨专业拦截（岗位名必须命中 biz_recheck 的专业方向词，tier3 另放行通用职能词，tier4 不拦）、「名字带领域词但干的明显是别的活」黑名单（电商美工这类——物流域有「电商」，但美工是设计岗）。实测物流 tier1 从公司专属岗名变成 物流管培生 / 仓储运营岗 / 供应链管理岗，化工 tier1 拦掉 6 个跑题岗。缓存键升到 rec-v11。
2. **三页面从「名义上」变「实际上」**——之前名单导入、匹配排行都挤在 fair.html 一个页面里（匹配端只是 ?report=1 的视图参数）。现在：学生端 fair.html 只管画像，聊完给「去匹配端」跳转卡片（离线双击模式保留原内联流程）；企业端 enterprises.html = 导入参会企业名单（match.js rosterOnly 模式，`/js/match.js` 服务端替换占位符后注入）+ 岗位上传框；匹配端是真正独立的 `demo/match.html`——同一套内联 JS，`window.__FORCE_REPORT` 启动即进报告视图，portal 的匹配端标签直接指向它。

第十四（2026-11-17 傍晚到夜间，18 个提交；代码位置见《第三版技术细节》同名补记）：

1. **判对口换了坐标系：企业打行业码、学生认专业族，查表判定**——旧判据两头都是自由文本，词表宽窄不对称：化学的窄词表把靶材、永磁、涂布全卡在门外，物流机械的宽词表靠「制造」「生产」通吃，土木靠「工程」二字全线放行。现在 20 类行业码 × 专业族一查表就出 核心 / 边缘 / 不符 / 判不了（判不了绝不判「不符」）；145 家 100% 打码（人工确认 37 + 模型 108），人工码优先级最高、重跑也不许覆盖；码表跟着流水线自动导出（外部工程拿到的枚举不会再是旧的那份），种子库也带码（clone 完不会再出现同一家在开发机判化工、在新同学机器判金属）。实测 3 套画像 × 145 家：47 家企业零消失，命中岗位 29→30，推断对 14→12，前后端查表对拍 4428 例 0 不一致。顺手修了「药学同时属于化学与医学、却被字典覆盖掉」，药学学生的化学方向一度整个消失。
2. **33 条「模型 vs 规则」的行业码分歧逐条核完，分歧清零**——32 家是模型对、规则被词面带偏（中天科技的「新能源」只是板块之一、全亿健康的「零售/连锁」是业态、多恩生物的「纺织印染」是应用场景），1 家两边都错（南京昀光硅基 OLED 微显示，电子信息 → 电气）。结论钉进人工码文件，原清单归档，当前分歧 0。
3. **主营复核先查「为什么没有方向词」，不直接毙**——一条对没通过复检时先定位根因：岗位名自带方向（规则漏判）、主营字段没采到（不能拿缺失当证据）、主营有字但词表没覆盖、只有分析检测这类宽泛词（证据太薄）、主营明确是别的行业（真不符）。开发期只有最后一种降级转现场待问，前四种保留待补并在报告里写明缺什么；诊断清单落文件，build 时打一行分类汇总。同时修了两个真根因：companies 表 145 家细分业务全空、描述只在增补档案里（页面读增补档案、后端只读 companies，等于拿半截主营判方向）；材料细分词补了 63 个（电解铝、靶材、稀土永磁、印染、催化剂…），「薄膜/镀膜」因「CVD 薄膜沉积设备」这类设备语境会误判，故意不进表。影响：9 对明确命中降级、248 对推断撤下，逐条可查。
4. **企业端重做成名单导入工作台，真根因不是配色**——注入时只搬了脚本，match.js 自带的那套样式留在临时容器里，145 行名单、按钮、说明全按浏览器默认样式摞成一团。改法是把样式插到 head 最前面（顺序决定覆盖：插后面会被基础尺寸顶掉，粘贴区又缩回 88px）；这一页重排成页头 + 三步流程芯片 + 白卡，上传键改成虚线块、粘贴区 230px 内部滚动、搜索立为主按钮、加名单行数徽标和搜索进度条、完成态转绿、移动端单独一档。桌面 1280 与移动 390 两档截图逐项看过。同时删掉「粘贴贵单位的岗位信息」整块输入区（产品不是给企业 HR 自助用的），门户与门禁文案同步。
5. **名单上传修三处硬伤，试跑一个字节都不落库**——中文文件名塞进 X-Filename 会让浏览器请求直接抛错（页面显示「本地服务没起来」，其实请求根本没发出去），改走查询串；CSV 先按 utf-8 读，检出替换字符回退 GBK（Excel 另存的 CSV 原来整片乱码归零）；单字「行/局/社/厂」噪声太大，改成词形态判断 + 表头整格屏蔽，xlsx 先认「企业名称」列。补档案加城市校验：名字以城市开头、与抓到档案的城市矛盾就判「没查到」——成都中科曾被配到北京的中科实业，岗位全算到成都那家头上，且只认开头，避免「XX（上海）有限公司」这类分支机构被当成总部。试跑：查档接口支持「只看不存」，结果只回给调用方；0 岗位不落库（存下来只是占位，下次还得重搜，还会盖掉库里原有档案）；缓存只落有岗位的企业；城市校验提到统一出口——库里已经躺着的错档案不走 build，只在 build 里校验等于没校验。数据侧清掉 16 条模拟残留，企业岗位回到 145 家（50 家模拟名单里 16 个假名字撞上了真实企业名，同名形状太像，直接把真档案覆盖成「没抓到页面」）。
6. **推荐去掉「静默放宽」**——专业为空直接拒绝，不再退回规则池：空专业时规则池给的正是销售 / 行政 / 人事 / 生产技术员那批泛岗。「换一批」只在本层换，升层改成显式「放宽一档」并说明代价，跨专业层带角标；第 4 层（通用职能）也受「愿意看不限专业」控制。停用默认画像里的假专业与假经历（缺就留空并标记）。模型把公告小标题当岗名抄（「质量」「生产」「研发」）的拦掉，会计 / 审计 / 法务 / 美工这类两字职业名白名单放行。采集端身份卡专业改必填：空着点保存就地拦下，卡片不关闭、已填内容不丢。
7. **匹配只排名单内企业**——按当前名单逐个取画像，取不到给「尚未采集」占位进资料不全层（不丢，也不冒充有档案），名单外的内置 145 家不再混入；没录名单才回落到内置名单，统计文案写明排序范围。14 条离线自测钉住名单内外隔离、占位、回落。
8. **报告行按试用反馈改口径五件**——①复核不通过不再铺红字，折成默认收起的「不通过（撤下 N 对）· 点开看原因」；②对口理由写清这家做什么细分行业、公告里的岗位、你勾的意向、你学的专业，兜底占位句不再外露，意向取第一个真实意向（曾有企业把画像里别的意向顶上，写成化学检验工程师）；③鼓励句只在「公告原文命中且理由无存疑」时给，理由里带推断 / 尚未找到 / 建议现场确认的一律不给（不再一边存疑一边劝去）；④命中岗位只列复核后仍有效的对（曾有企业一边写「命中 2 个」一边写「撤下 1 对」）；⑤方向沾边、只有管培生的行写出轮岗入口「管培生（培养方向待核实）→ 你选的 X」，排在命中行之后，政府机关 / 事业单位 / 学校不出这句（考试招录，没有管培生一说）。
9. **删掉「岗位更细就不算同一个岗位」这条大小类规则**——仓储物流 × 物流专员、AI 算法 × 算法被这条判成「不是同一个岗位」，可另一处又把同一对升级成命中，于是命中岗位栏列着岗位、对口理由却写「不是同一个岗位」，两栏自相矛盾。现在大类意向可以进小类，存疑的先放命中，交给主营复核与学生专业收紧。真实画像影响：命中企业 22 家不变，命中岗位 32→33，全库不再出现这句话。
10. **同一条判据有四份拷贝，补齐漏掉的第四份**——后端判定、后端理由、前端判定、前端理由各一份。删规则时只改了三份，前端理由仍直接返回空串，页面只能拿模型原句兜底——判据改了、文案没改，用户看到的还是旧话。修完 6792 对里从 4361 对不一致降到 0；对拍夹具加了逐对方向理由，测试逐字比对、不一致就红。另修「意向没限定方向」两处分叉：后端看方向关键词、前端看方向核，运营管理培训生这类「核里有字、词表里没词」的意向两边走岔，整句理由丢失。
11. **代码侧收口三件**——榜单构建函数 549 行拆成「装载 / 匹配 / 组装」三段，拆前后 payload 逐字段一致（只差生成时间）；新增数据库访问唯一出口（正常提交、异常回滚、一定关闭），首批收口 8 处，剩下 38 处用一条测试按文件限额钉住——新代码加一处裸连接就挂，收一处必须把额度下调，是一份可执行的待办；采集端脚本从「对交接包做 20 处字符串替换」冻结成真实源文件（重建前后页面逐字节相同），补丁脚本退成一次性迁移工具；新增离线副本同步脚本，单向镜像、排除活库与备份、副本自带的启动脚本受保护不被覆盖。
12. **验收基线**——198 条用例全绿（187 条 unittest + 11 条函数式）；前后端对拍 6792 对四项（职责 / 方向判定 / 轮岗 / 理由）0 不一致；匹配自测 0 失败；名单池 14 条全过；三端页面与健康检查均 200。

已知未修，明确留给下一轮：试跑结果仍会写进服务进程的内存缓存（同进程内再查同名企业会拿到试跑结果，重启才干净）；同一进程里「没查到」的负结论会粘住（第二次查询 0.05 秒秒回空）；独立门户服务的名单接口仍只读 X-Filename（传 xlsx 得 0 家）；xlsx 解析不清序号（「1.南京晨曦…」带着编号进库）；导入表头只认含「单位名称」那种写法；企业名 4 字门槛会把「华为」「小米」这类短名挡在门外。

## 十七、名次改成「先看复检结论，再看分数」

这份改动不是代码 bug，是**排序口径**的问题，由一次人工核对引出来：材料科学与工程的虚拟用户，榜单第 1 名是烟台睿创微纳（半导体与集成电路）。它一条岗位都对不上，只有「按行业推断」，点开报告的复检折叠块写着「行业码有限对口（只放通用职能岗）——通用职能岗照放，但半导体研发 & 工艺这种领域岗不在其列」。**复检自己都没确认对口，它却排第一**，靠的是城市 34 + 企业类型 23.1 + 行业地位 28.1 攒出来的 85.2 分。

原因是排序键把分数放在「状态」前面：`-score` 比 `state` 先比较。分数只衡量城市 / 企业性质 / 行业地位，**本来就不含岗位匹配度**，于是「硬件条件好」被读成了「对口」。

用户定的新规矩（原话）：

> 推断有岗命中的正常排，而是复检判断有限对口的这个，复检失效了，他不确定的往后排，正常的没岗位推断的，和我的方向一致，岗位一致，那就正常排。

落到代码里是**三档**，依据是**复检结论码**，不是「有没有岗位名」：

| 层 | 条件 | 含义 |
|---|---|---|
| 0 正常 | `code_core`（行业码对口）/ `name_dir`（岗位名自带方向词）/ 没有复检结论 | 方向和岗位对得上，按分数正常排。**推断来的也算**——只要复检没判它不确定 |
| 1 不确定 | `code_edge`（有限对口，只放通用职能岗）/ `code_out`（不是这个方向）/ `biz_other`（主营是别的行业） | 复检没能确认，整层沉到正常层之后 |
| 2 管培生类 | 看得见的岗全是管培生 / 储备干部 / 轮岗 / 校招生 | 谁都能投，垫在最后 |

`biz_other` 是第二遍核对时补进来的：法学和新闻两个用户的榜首都是「睿创微纳」（半导体），复检写的是「主营是别的行业」。它在 `biz_recheck` 里本来就算 `drop`，只是历史原因行没真撤下——既然复检都说了主营不是这个行业，同样属于「没确认对口」，一起下沉。`biz_weak`（主营只是沾边）、`biz_missing`（查不到主营）、`biz_no_word`（主营里没有方向词）暂时没并入：当前 10 份榜单里一次都没出现，先不扩大范围，真出现了再定。

同层内仍按分数排，现场确认不招、主营判死的照旧垫底。

材料专业那份榜单改完的效果：**睿创微纳从第 1 位降到第 40 位**（第 40 位理由写「复检判「行业码有限对口（只放通用职能岗）」，不算确定对口」），第 1 名变成天山铝业——它同样是「推断、无岗位名」，但复检判的是 `code_core`，方向一致，按用户口径就该正常排。42 行里 tier 0 / 1 / 2 分别是 37 / 3 / 2。

配套改了三处，缺一处就会名次打架：

1. **后端 `fair_bridge.rank_tier()`**：分层判定；`rank_sort_key()` 抽出排序键，让规则可以被测试直接调用（散在 `sort` 的 lambda 里没法单独验证）。
2. **前端 `report.js` 的 `fitTier()`**：页面会把 rows 拿过去**自己再排一遍**（历史原因：名次只由排序决定），两端不同源就会出现「后端第 3、页面第 5」。两处重排（默认队列序、只看命中）都接上了分层。
3. **`rank_reason` 文案**：从「排序分 85.2 / 按行业推断待核实」改成「复检判「行业码有限对口」不算确定对口 / 排序分 85.2」，让人一眼看出为什么排在后面，而不是以为 85.2 分代表对口。

新增 `tests/test_rank_tier.py` 15 条，锁住分层判定、排序优先级（85.2 分的 `code_edge` 不许压过 53.7 分的 `code_core`）、管培生垫底，以及**前后端常量一致性**（脚本直接读 `js/report.js` 比对词表）。全量 303 用例 / 6599 subtest 全绿。

一个遗留：`only_ask`（没命中、没推断岗、只能现场问一句）这一层保留在原位（比分数优先）。它是既有规则，这次没动，所以会出现「80.2 分的 only_ask 企业排在 13.2 分的企业后面」。要不要把它挪到分数之后，等人工核对完再定。

## 十八、生物专业按细分产业带排（2026-11-18）

用户拿「生物」画像实测后的一句反馈引出的改动：

> 药企和化学明显对胃，生物的话应该是生物制药更对胃吧。

**问题不在「药企太多」（库里就 19 家医药，这是事实），而在「医药被当成一个行业」。**
医药内部其实是几条不同的产业带：生物药（抗体 / 疫苗 / 细胞 / 基因 / 发酵）、
化学药（原料药 / 中间体 / 制剂 / 输液）、中药、器械诊断、医药流通；生物和化学各自
对得上的不是同一批企业。行业码只有「医药」一格，判到这里就断了。

生物那份榜单改前（11 家，全是医药）：

```
1 科伦药业（大输液）      2 久安药业（注射剂）    3 中科开浦（疫苗/细胞基因）
4 上成生物（快检试剂）    5 普洛药业（原料药）    6 多恩生物（纺织印染助剂）
…
9 江苏功成（卫生杀虫剂） 10 诺尔曼（IVD）        11 华润三九（中药 OTC）
```

改后（9 家）：

```
1 中科开浦 生物药        2 上成生物 器械诊断      3 诺尔曼 器械诊断
4 科伦药业 化学药        5 久安药业 化学药        6 普洛药业 化学药
7 华海药业 化学药        8 奥翔药业 化学药        9 华润三九 中药
```

**判据只看主营描述，不看企业名。** 这是这次最关键的一条：多恩、功成能上榜，靠的就是
企业名里的「生物」两个字——主营闸门吃的是「企业名 + 行业 + 细分」，名字把主干淹了。
新模块把名字排除在证据之外，于是「多恩生物科技 → 主营命中『纺织』」「江苏功成 → 主营
命中『杀虫』」如实判成非医药，从主榜撤下并写进 `biz_fit_no` 留档
（「名字里带「生物」，主营其实是非医药（化工助剂/食品保健/医美），不是医药这行」）。

**只影响排序，不删企业**（除名字骗人那两家）。化学药企业对学生物的人不是错，只是隔
一层；所以它们仍在榜上，只是整体沉到生物药与器械诊断之后，名次理由写
「细分 主营命中「原料药」；隔一层（偏化学药/中药）」。

**范围刻意收窄**：只判 `industry == "医药"` 的企业（别的行业不越权重判），只给生物类
专业登记档位（化学 / 药学不动——它们本来就是化学药打头）。剩下两条扩展路径写在
`sector_fit._PREF` 里，加一行就能开。

配套改了四处：

1. `sector_fit.py`（新）：分带词表 + 专业档位表 + `annotate()`，与 fair_bridge 解耦，可单测。
2. `fair_bridge`：行里多一个 `sector`（band / label / rank / why）；`rank_sort_key` 在
   「分层」之后、「分数」之前插入 `sector_rank`；`rank_reason` 追加细分结论；
   非医药带在拼行前撤榜进 `biz_fit_no`。
3. `js/report.js`：两处重排（默认队列序 / 只看命中）都接上 `sector.rank`，名次理由同口径
   ——页面会自己再排一遍，两端不同源就会出现「后端第 1、页面第 4」。
4. `job_recommend`：展示名后缀「（医药/医疗）」→「（生物制药）」，生物医学工程 →「（医疗器械/诊断）」。

新增 `tests/test_sector_fit.py` 23 条（19 家用例全取自真实库：科伦 / 华海 / 上成 / 益丰 /
多恩 / 功成等），锁住「名字不算证据」「只对医药生效」「生物档位顺序」「化学不分带」
「前后端同源」。全量 346 用例 / 6898 subtest 全绿。

一个取舍：**同一条带优先于分数**，所以 63.6 分的器械诊断排在 73.5 分的化学药前面。
这和第十七条「分数不含岗位匹配度，不能跨层压人」是同一个道理——细分方向属于「对口」
的一部分，不是偏好。如果哪天觉得压得太狠，把 `sector_rank` 挪到 `-score` 之后即可退化成
「同分才比细分」。

## 十九、名单落库 + 实习/竞赛「干啥推啥」（2026-11-18）

### 1. 那句「匹配池里共 132 家」原来是空头支票

企业端导入 132 家，页面写着「名单就绪，去匹配端看排行」。点过去看到的却是 9 家
（生物画像当前生效的那份）——因为那 132 个名字**只活在浏览器里**：`match.js`
只有 `localStorage.setItem("companies", …)`，从来没有读回来；匹配端读的是
`/api/fair/payload`，跟名单一点关系都没有。更早还有个连带问题：匹配端排行走
`report.js`（有主营复检、细分产业带、分层），企业端名单池走 `match()` 那套老引擎
（只有城市 40 / 方向 35 / 紧急度 25 + 六个偏好维度），两套引擎口径不同。

改法是把名单**落库**，榜单按名单收口：

| 位置 | 改动 |
|---|---|
| `roster_store.py`（新） | `fair_roster(fair_id, name, note)` 表；整表替换（名单是「这一场」的完整集合，增量会留上一场残名） |
| `POST /api/fair/roster` | 落库 + 后台重建（只 build，不跑 `match_fill`——名单不影响命中结论） |
| `GET /api/fair/roster` | 名单条数 + 重建状态，供前端提示 |
| `fair_bridge.apply_roster()` | 榜单只排名单里的企业；四个排除清单一起收口；没进榜的进 `roster.missing` 留档 |
| `js/match.js` | 搜索完 `POST` 名单，提示「已落库 N 家，排行正在后台重排」 |
| `js/report.js` | 报告头写「本榜只排这场名单里的 N 家，已进榜 M 家，另有 K 家没进榜」 |

两个刻意的选择：

- **名单为空 = 不按名单过滤**。没导入名单、冷克隆、CI 构建（种子库里没有这张表）
  都会走全库口径，产物与改动前逐字节一致，不会因为新功能让 CI 变红。
- **没进榜不消失**。`roster.missing` 逐条给原因：被硬条件剔除 / 校招公告没有对口岗 /
  主营不交叉 / 入库时就知道没抓到（城市对不上、没抓到可信页面）。企业端搜索的那一刻
  其实已经知道原因了，这个理由跟着名单一起落库，报告里直接念出来，不再是一句笼统的
  「没匹配上」。

实测（本机 8102）：名单 3 家 → 榜单 3 行；加一个不存在的公司 → `in_rank=2`，
`missing` 写着「搜到的公司在深圳，与名单对不上，按没查到处理」；清空名单 → 回到 9 行。

### 2. 实习干啥，L1 就推啥

用户的原话：「一个文科生干了一个供应链的实习……实习干啥，l1 推啥（干 1 个推一个，
其他的还是专业推，也还在 l1），竞赛也是……论文就暂时不考虑，竞赛假如一个数据分析
竞赛，你就推一个（只一个）相关岗位。」

改动分三层：

1. **`experience_jobs()`**：实习 / 竞赛各翻成一个通用校招岗名（`_FUNC_TITLE` 职能词表
   51 条、`_COMP_TITLE` 竞赛 6 条），一段经历只给一个；同一职能多段去重，不同职能各给一个。
   「PLC 调试实习」→ 电气工程师，「审计实习」→ 审计助理，「数学建模竞赛」→ 数据分析岗。
2. **`_with_experience()`**：这一层进 L1 且排在最前，**不过专业闸门**。文科生的
   「供应链专员」原来会被 `_major_ok` 判成跑题丢掉，可那正是他真正走得通的路；
   化学的「研发工程师」本来就在池里，就地标成经历岗提前并换理由，不重复加一条。
3. **`experience_drop()`**：`SIGNAL_RULES` 里一条「供应链」会带出 4 个岗（供应链/计划岗、
   采购专员、物流运营岗、供应链数据分析岗），那是给「技能/课程」用的写法。一段实习
   给 4 个岗，L1 就被撑满、专业岗被挤到看不见——所以同一组信号只留经历对应岗那一个，
   补位时也挡住（否则补位又把这批岗补回来）。

实测（离线规则池，不联网）：

```
汉语言文学 + 供应链实习      供应链专员(经历) / 语文教师 / 中文编辑 / 文案策划 / 内容编辑
汉语言文学 + 供应链 + 数据分析 供应链专员(经历) / 数据分析岗(经历) / 语文教师 / …
化学 + 有机合成研发实习      研发工程师(经历) / 合成研究员 / 化验质检 / 分析测试 / 工艺 …
机械 + PLC 调试实习          电气工程师(经历) / 机械设计 / 结构 / 工艺 / 设备 / 质量 …
论文                          不产生岗位
```

边界：论文不参与（用户明确暂不考虑）；`没有 / 无 / 跳过` 这类占位当作没填；
tier2（相邻有门槛）不再重复经历岗——它在 L1 已经给过一次。

新增测试：`tests/test_experience_jobs.py` 10 条、`tests/test_roster.py` 9 条。
