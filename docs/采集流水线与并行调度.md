# 采集流水线与并行调度

> 这份文档管的是「**从一张展位表到一页可用的匹配报告，怎么跑最快、哪一步能并行、
> 哪一步必须串行、失败了从哪儿接着跑**」。
> 判定口径见 `docs/报告口径与权重分配.md`；哪份文件是准据见 `ARCHITECTURE.md`。

---

## 1. 一条命令

```bash
cd ent_tools

# 全量：采集 → 方向 → 报告 → 页面 → 测试
python -X utf8 refresh_all.py --collect

# 只补主营（有岗位但主营为空的企业，走页面缓存，不重抓）
python -X utf8 collect_roster.py --scope-only

# 只重跑上次没抓到岗位的
python -X utf8 collect_roster.py --retry-miss

# 只改规则、不联网
python -X utf8 refresh_all.py
```

`refresh_all.py --collect` 把原来两个入口（`collect_roster.py` + `refresh_all.py`）
串成一条：采集完直接重算方向、重建 payload、重建页面、跑一致性测试。以前漏跑其中一步的
后果是「库里有新企业、报告还是旧的」，而且不报错。

## 2. 链路与产出

```
booths.json（展位表，145 家）
   │  ← collect_roster 自动从它重建 _roster_todo.json（快照丢了不耽误跑）
   ▼
portal.build(name) ─────────────────────────────── 联网，慢
   ├─ pages_for(name)      多 query 搜索 → 抓页 → 无头渲染 → 选正文   ← 缓存命中 3.2s
   ├─ enrich.call_model    模型结构化：岗位 + 主营（biz_scope）
   ├─ scope_from_about     招聘页没写业务介绍时，去官网「关于我们」补一次
   └─ 失败退规则抽取（guess_scope / extract_jobs），不编造
   ▼
save_item → company_jobs.item_json     ← 唯一写库点，合并而非覆盖
   ▼
_dir_fill.py      按主营推岗位方向 → job_dir_hint 表（纯本地，秒级）
   ▼
fair_bridge.build 画像 / 主营判定 / 无岗推断（模型并发 + 指纹缓存）
   ▼
build_fair_page.py → demo/fair.html
```

**谁产出什么**：

| 字段 | 生产者 | 缺了会怎样 |
|---|---|---|
| `jobs` | 模型抽取，失败退规则 | 报告里这家只能「推断待核实」 |
| `biz_scope` | 模型从页面原文抽；招聘页没有就去关于页 | 岗位方向判不出 → 全部退成「现场问」 |
| `bizEvidence` | 模型给的原文片段 | 对不上原文 → 主营作废（防编造） |
| `job_dir_hint` | `_dir_fill.py` | 报告侧回退现算（慢但不断） |
| 画像 / yes-ask-no | `fair_bridge` 内联 | 无 |

## 3. 耗时构成（实测单点）

`portal.build` 一家企业：

| 场景 | 耗时 | 说明 |
|---|---|---|
| 冷跑（无页面缓存） | 16.0 s | 搜索 6 次 + 抓 3~6 页 + 模型 1 次 |
| 热跑（页面缓存命中） | 3.2 s | 只剩模型一次调用 |
| 主营为空再补一次关于页 | +1~5 s | 纯名搜索 + 抓 1~3 页 |

补主营 4 家（含 2 家冷缓存）：冷 65 s → 热 **7 s**。

耗时排序：**无头渲染 > 搜索 > 抓页 > 模型**。无头渲染曾是绝对大头（单次 5~18 s）。

### 无头渲染：从「每次开一个浏览器」到「一个浏览器开多个标签页」

2026-11-16 改的，改的是**怎么拿到渲染后的 DOM**，不改「选哪一页」。

| | 旧（`--dump-dom` 一次性） | 新（CDP 复用标签页） |
|---|---|---|
| 做法 | 每次 `spawn msedge --dump-dom`，进程用完即死 | 一个 Edge 常驻，每次只开一个标签页 |
| 冷启动 | **每页都付一遍** 1.5~3 s | 全程只付一次（约 165 ms） |
| 并发口径 | 进程信号量 2 | 标签页信号量 6（`FAIR_JS_TABS`） |
| 单页实测 | 5.9 s 均值 | 2.7 s 均值 |
| 12 页 / 6 线程 | 25.2 s | **11.1 s** |
| 超时页 | 长页面常整页超时返回空 | 等正文稳定，能拿到 |

实测 8 个真实招聘页：7 页渲染出的正文**逐字等长**（8463/3846/3347/473/1723/29 全部相同），
第 8 页是微信「环境异常」拦截页，两边都拿不到正文，差异只是标题 6 个字。

**安全阀**：`portal.fetch_js` 先走 CDP，返回 `None` 就退回旧的 `--dump-dom`
（`_fetch_js_locked`），连续失败 3 次后本进程不再尝试。所以 CDP 出任何问题，
最坏结果等于改动前，不会让采集结果变空。`tests/test_cdp.py` 专门锁这条。

- `FAIR_JS_TABS=6` 同时渲染几页（实测 6 是甜点，8 反而更慢）
- `FAIR_JS_CDP=0` 强制回旧路径，A/B 对照和应急都用它
- `python -X utf8 _js_ab.py --from-db 8` 跑真实页面 A/B，比耗时也比正文长度

## 4. 并行设计

### 能并行

| 层 | 做法 | 为什么安全 |
|---|---|---|
| 企业之间 | `--workers 6`（原 4） | 各家互不依赖，I/O 等待为主 |
| 单家内部：搜索 | 最多 6 个 query 用 `ThreadPoolExecutor.map` 并发 | `map` 保序，候选集与串行**完全相同**，只省时间 |
| 模型调用 | 画像 / 主营判定各自已有线程池（`job_profile` / `biz_fit`） | 按企业独立，结果与顺序无关 |
| 浏览器渲染 | 6 个标签页并发（`FAIR_JS_TABS`） | 每个标签页独立，渲完即取即关，互不影响 |

### 不能并行 / 必须限流

| 点 | 限制 | 原因 |
|---|---|---|
| HTTP 请求 | 信号量 12 | 家间并发上去后，同时在飞的请求不能无上限 |
| 无头浏览器进程 | 全场只有 **1 个**常驻进程 | 再多一个进程就要多付一次冷启动，且内存翻倍 |
| 浏览器标签页 | 信号量 6（`FAIR_JS_TABS`） | 实测 8 个并发的总耗时反而比 6 个高 |
| 抓页面选优 | 仍按 `_hint` 排序串行试 | 页面质量决定抽到的岗位，并行会改变「选到哪一页」→ 改结果 |
| 写库 | 每批落库（`save_item` 立即写） | 中途失败不丢已采部分 |

**判据**：并行只能改「谁先谁后」，不能改「最终选中哪个」。凡是会影响选页结果的，
一律串行。所以 `pages_for` 里搜索并发、抓页串行。

### 断点与重试

- 页面正文按企业名缓存 12 小时（`data/_pages/`，`FAIR_PAGE_CACHE_TTL=0` 可关）
- 没抓到岗位的名单落 `_roster_miss.json`，`--retry-miss` 只重跑它们
- 单家失败如实记 miss，不阻塞整批

### 增量

| 任务 | 跳过条件 |
|---|---|
| 全量采集 | 库里已有 `jobs` 的企业直接跳过（`--force` 覆盖） |
| 补主营 | `--scope-only` 只挑「有岗位但主营为空」 |
| 重算方向 / 报告 | 指纹缓存命中即跳过（`cache_guard`） |

## 5. 数据流向：只进不出

**写库只有一个入口**：`save_item(name, patch)`，语义是「合并」不是「覆盖」。
两条保护：

1. 主营只补不抹：这次没从页面找到业务介绍，不会把上次找到的那句冲掉
   （`biz_scope` 为空时 `pop` 掉，不参与合并）。
2. 补全过的属性不被采集猜测值覆盖（`enriched` 标记，城市这类字段）。

⚠️ `load_to_db.py` 是**另一条旧链路**（`companies.json` 118 家），与当前 145 家展位表
不是同一批企业。跑它会把 96 家不相干企业插进库。日常只用 `collect_roster` 那条。
它的 `item_of()` 保留着，只为 `biz_scope` 键名转换的历史兼容。

## 6. 踩过的坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 采集抓到了主营，报告仍当没写 | 契约用 `bizScope`、库和下游读 `biz_scope` | 全链路统一 `biz_scope`，`item_of` 兼容旧键 |
| `"公司" 公司简介` 搜出「宁波市」词条 | 中文长名 + 修饰词，Bing 退化成地名召回 | 补主营只用**纯企业名**搜索 |
| 主营被写成「集团简介 发展历程 全球布局…」 | 导航条命中了锚点 | `_scope_ok`：导航词 ≥2 / 无业务动词 / 平均词长过短 → 判为未知 |
| `--scope-only` 打印「主营=有」但库里没有 | 该分支提前 `return`，跳过了 `save_item` | 分支内自己落库 |
| `collect_roster` 跑不起来 | `_roster_todo.json` 不存在（派生文件没进仓） | 缺了就从 `booths.json` 当场重建 |
| `refresh_all` 说「无需重启 8102」 | 端口硬编码 | 读 `FAIR_PORT` |
| **全量 `--force` 重采一次，岗位数腰斩、带 URL 岗归零**（2026-11-16 实测） | ① `save_item` 是 `merged.update(patch)`，MISS 时 `patch.jobs=[]` 会把旧库已核对岗位冲成空（96 家归零）；② `enrich.build_entry` 产出的岗位**没有 `source_url` 字段**，URL 只挂在企业级 `source` 上，所以新采岗位全部无 URL | 见下方「7. 全量重采的破坏性与 URL 缺口」 |

## 7. 全量重采的破坏性与 URL 缺口（2026-11-16 实测结论）

**背景**：为回答「为什么这么多岗无 URL」，按现有并行流程 `--force` 全量重采一份新库
（`FAIR_DB=.../data/careersafari_v2_parallel.db`，145 家 / 6 workers / 14.7 分钟），
与旧库逐项对比后决定是否替换。

**结果：新库不优于旧库，旧库保留，未替换。**

| 指标 | 旧库 `careersafari.db` | 新库 `v2_parallel` |
|---|---:|---:|
| 企业数 | 145 | 145 |
| 岗位总数 | 1139 | 458 |
| 带逐岗 URL | 467 | **0** |
| 有岗企业 | 117 | 49 |
| 主营非空 | 144 | 144 |
| 其余表（evidence / dir_hint / JD / positions / llm_match） | 齐全 | 齐全（整库复制） |
| 逐家变化 | — | 变差 100 / 变好 15 / 持平 30 |

对照：`campus_recheck.db` 校招核实库 615 岗**全部带 URL**、覆盖 90 家，是当前唯一
逐岗 URL 完整的数据源。

### 三个真问题（不要当成偶发，均已修）

1. **MISS 冲空**：`collect_roster.work()` 抓不到岗位时 `item={"jobs":[]}`，
   `save_item` 的 `merged.update(patch)` 直接把旧岗位覆盖掉。
   → **已修**：patch 的 jobs 为空而旧库有岗时，`jobs/jobSource/jobEvidence/source` 一律不写，
   只更新本次确实采到的状态字段（note、属性等）。
2. **采集不产逐岗 URL**：`enrich.build_entry` 的岗位对象只有
   title/requirements/headcount/urgency/group/salary，没有 `source_url`；
   URL 只在企业记录顶层 `source`。早期 handoff 合并（`merge_handoff_jobs.py`）
   才写逐岗 URL——这就是旧库 467 岗有 URL、新采 0 岗有的根因。
   → **已修**：模型路径（`enrich.build_entry`）和规则路径（`portal.build`）在落库前，
   把本次抓到的页面地址回填成每个岗位的 `source_url`；只认 `http` 开头的真实地址，
   没抓到就留空，绝不编 URL。
3. **HIT 覆盖**：即使抓到岗位，`merged.update(patch)` 也会用本次的少量新岗位整体覆盖
   旧库已核对过的岗位，同样会让库变差。
   → **已修**：有岗时按岗位名合并——同名旧岗由本次带 URL 的新岗顶替，旧库独有岗位保留。
   总原则：**采集只做增量补全，不做删减**；要删岗只能走单独的核实流程
   （如 `build_campus_recheck.py`）。

### 2026-11-16 二次重采（三条修复后）：已替换主库

修复上述三条后全量重采 `careersafari_v3_incremental.db`（12.3 分钟），对比：
岗位 1139 → **1329**、带逐岗 URL 467 → **892**、有岗企业 117 → **119**，
其余指标表（evidence / dir_hint / JD / positions / llm_match）全部持平。
逐家变好 35 / 持平 109；唯一"变差"的烟台睿创微纳是旧库 169 岗里 35 种标题重复
（"嵌入式软件"重复 10 次），按名字合并去重后 63 个唯一岗且带 URL，属质量提升。
结论：全部占优，已用 v3 替换 `data/careersafari.db`，旧库备份为
`data/careersafari.bak_before_v3_20261116.db`。

### 复用约定

- 想重采对比：**先 `cp careersafari.db xxx.db`，再用 `FAIR_DB=<新库>` 跑**，绝不直接写活库。
  `collect_roster.py:32` 已支持 `FAIR_DB` 环境变量（默认仍是 `careersafari.db`）。
- 只有新库在所有核心指标上**全部占优**才替换；v2 不占优已弃用，v3 占优已替换。
  `careersafari_v2_parallel.db` 等对照库保留作证据。

## 8. 非校招企业的画像推断岗补库（2026-11-16 用户拍板）

**用户拍板的三件事**：① 画像（不带学生意向、只按主营列岗位）挪到采集侧提前建；
② 只对 **0 岗 + 非校招来源**的企业建，校招企业不碰；③ 推断岗**补进岗位库**并**逐岗标注**
来源，匹配端要能看出"这是大模型推断、不是真实 JD"。

**为什么不当成真实岗位用**：`job_profile` 的岗位是"这类单位通常的编制"，不是这家今年的
招聘计划。直接塞进 `jobs` 会被判定链当成真实 JD——`audit()` 里
`has_jd = bool(titles) and not _is_non_jd_source(c)` 一旦为真，模型给的岗位只要落在库里，
就会从 inferred 升成「明确命中」，等于用模型猜的岗位冒充企业的真实招聘证据。这是要守住的线。

### 补库范围（实测数字）

- 0 岗企业 26 家、非校招来源（websearch/社招/未知）99 家，并集 **99 家**。
- 其中 55 家被校招核实库认作校招 → **必须排除**（它们用真实 URL 岗，推断岗会污染）。
- 实际补库 **44 家**；画像已覆盖 37 家，其余现场补建。

### 实现约定（三条硬约束）

1. **逐岗标注**：补进去的岗位带 `job_source_kind="大模型推断"`、`job_profile_basis=业务链条`、
   `source_url=""`（无证据 URL）。真实岗位一个字段都不改，只追加。
2. **判定链隔离**：`_clean_jobs` 只留真实岗（推断岗不进 `titles`、`has_jd`、命中证据）；
   推断岗只在"现场问句 / 推断待核实"里出现，绝不参与 hit 判定、绝不进 `matched_jobs`。
   校招库覆盖（`apply_campus_recheck`）照旧把 90 家认校招企业的 jobs 换成真实 URL 岗，
   本步骤的推断岗不进那 90 家，互不干扰。
3. **可回滚**：环境变量 `FAIR_INFER_FILL=0` 关闭补库；补库前后各存一份快照到
   `data/infer_fill_before.db` / `data/infer_fill_after.db`，逐家可核对。

### 流程位置

`refresh_all.py` 的步骤：`建画像（本步）→ step_dirfill 重算岗位方向 → step_build 重建 payload`。
顺序不能反——方向表和 payload 都要看到补进去的推断岗标注。

### 实测（2026-11-16）

- 补库 44 家、推断岗 591 条；校招 90 家**零污染**；快照 `infer_fill_before/after.db`。
- 前端 payload 36 家里 19 家带"大模型按主营推断"标注，推断岗与真实 `job_titles` 零交集。
- **踩过的坑（已修，写在这里防止复发）**：`_resolve_state` 里 `real` 的计算原有一条
  「`jd_titles` 为空就放宽、把对齐结果全当真实证据」的口子，是给老 0 岗企业留的。
  补了推断岗后，0 岗企业的 `job_titles` 空 + matched 全是推断岗，正好命中这条口子，
  3 家企业被误升成「明确命中」（拿模型猜的岗冒充真实 JD）。
  → 已修：`_has_infer = bool(_inferred_jobs(...))`，补过推断岗且真实岗为空时不再放宽；
  真实岗仍在则照常算证据。测试 `test_inferred_jobs.HitUpgradeTests` 钉住。
- 88 个单测全过；修复后带标注的 19 家里 18 家 inferred、1 家 hit（该家真实岗里确有
  对口岗「脱硫脱硝工艺工程师」，hit 成立）。
