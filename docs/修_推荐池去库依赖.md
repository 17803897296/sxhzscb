# 修：采集端推荐池与岗位库解耦（v15，2026-11-16）

## 用户指令
"你看看你采集端推荐是不是参考了数据库的岗位库，不能这么做。"

## 坐实的依赖（v14 行为）
`job_recommend.py` 的 `db_job_index()` 直接读 `data/careersafari.db`：
- 1300+ 库内岗位名（**含大模型推断岗**）整体塞进推荐提示词的两栏清单；
- 模型被指示"优先从这里挑"并标 `from_db=true`，前端按 `db_level`
  打"校招公告明确在招"等来源标签和"校招"小标；
- 规则兜底 tier0 也做库内岗位名核心词匹配。

## 危害
推荐候选被库内岗位带偏 → 学生勾的"意向岗位"来自库里/推断岗 →
采集端反向给匹配端喂答案，循环污染，意向数据失真。

## 改法（v15）
1. `job_recommend.py`：删除 `db_job_index` / `db_job_titles` /
   `LV_CAMPUS` / `LV_OTHER`；`recommend` / `get_pool` / `llm_pool` /
   `rule_pool` 全链路去掉 `db_jobs` / `campus_jobs` 参数；
   提示词删掉两栏库内岗位清单与 from_db 指令；输出候选只含
   `{title, why}`；`PROMPT_VER` 升 `rec-v7`（池子缓存失效）。
2. `js/recommend.js`：删 `_srcNote`（三档 db_level 文案）与"校招"小标渲染。
3. `build_fair_page.py` 重建 `demo/fair.html`（RECOMMEND_JS 内联）。

## 明确保留
- `_companies_from_db`（页面内置**企业**名单来自活库）不动——那是
  企业范围对齐（145 家），不是岗位推荐参考。
- 页面残留的两处"（校招）"是库内真实岗位名"设备维修员（校招）"，不动。

## 验证
- 离线规则池：正常出候选，无库内岗位。
- 真实模型调用（CLI + 服务端 POST）：候选全部通用岗位名，
  响应无 `from_db` / `db_level` 字段。
- 全仓 grep：推荐链路无任何读库残留。
- tests/ 14 个测试文件全过。

## 补记（2026-11-17，v16 联网推荐）

v15 的纯模型口径还是会在两处翻车：造词（招聘网站搜不到的职能描述）和跑题
（与专业关系不大的岗位混进池子）——用户点名。改成联网推荐：

- 主路径：DeepSeek 独立 Search API（`POST /v1/tools/search`，同 key，
  5 元/千次）先搜「本专业校招岗位」+「所属大类校招岗位」，证据（标题+摘要+
  来源）注入提示词，模型只准从证据里提岗位名；证据落盘缓存 6 小时
  （`data/web_evidence_cache.json`）。
- 三道闸：提示词规矩（只取证据里的叫法、why 引来源）→ `_grounded` 落地
  校验（证据原文找不到就丢）→ `_bad_title` 类别标签拦截（「计算机类岗位」
  「信息技术」「宣讲会」）。
- 降级链不变：搜索失败 → 纯模型口径 → 规则兜底；`PROMPT_VER=rec-v10`。
- 页面标签区分来源：`（联网搜索 · 真实校招口径）` / `（模型生成 · 校招口径）`
  / `（规则兜底 · 校招口径）`——降级在 UI 上看得见。
- 实测（物流/食品/计算机三专业）：全部 `mode=llm-web`，岗名全部来自真实
  校招公告（得力集团、京东新锐之星、德邦、万纬、养生堂农夫山泉、思念食品、
  掌上先机等），why 全带来源引用；每次拦掉 1～5 个造词。
