# 第三版技术细节

> 这是《第三版更新说明》的详细技术版，逐项保留代码位置、实测数字与改动原因。
> 真正影响学生看到什么的是前四节——匹配推断、命中算法、数据库、采集流程；
> 代码重构只是让这些改动以后还能改得下去。
> 所有数字都来自 2026-11-16 的代码与实测，不是估计。

## 一、匹配段：大模型推断换了路线

**旧路线**：把学生意向塞给模型，问「这家单位接不接得住」。作答空间被意向框住，模型会顺着最短路径编岗位名——报告里出现过「电解铝设备工程师」「钻探设备维护工程师」「激光雷达装调工程师」这种业务词 + 岗位词粘出来的名字，招聘网站搜不到。用户当时的原话是「推断还是太多，不真实」。

匹配段现在一共 **5 类模型调用环节**，各自解决一个不同的问题（不是一次调用包打天下）：

| 环节 | 做什么 | 并发方式 |
|---|---|---|
| 意向语义映射 `intent_semantics` | 学生的意向岗位 ↔ 企业真实岗位名 | 每个意向单独一次短调用，8 并发；多意向塞一批会超时 |
| 命中复核 `hit_verify` | 判断「共享字但不同职能」是不是误命中 | 批量 160 对一次、上限 640 对；当前 126 对约 2.4 秒 |
| 0 岗推断 `unknown_infer` | 无具体岗位企业按主营判断可能招什么 | 逐家单条 + 8 并发（不能混批，见下文） |
| 主营交叉 `job_profile` / `biz_fit` | 这家单位的业务能不能容纳学生方向 | 逐家单条 + 8 并发；先粗筛再并发预取，循环里只查表 |
| 命中判定 `llm_match` | 写入 `llm_match` 表的 hit / inferred / miss | 8 家一批 + 5 workers，提交画像时后台重算 |

**新路线（默认）**：把顺序倒过来。

1. **先不看学生要什么**，只问模型「按这家单位的主营业务，业务链条上实际设哪些岗」。`job_profile.py` 的提示词版本 `jobprof-v3`，要求输出「业务链条 + 12~20 个岗位名（岗位名 | 强度 | 环节）」，并明确禁止拼造、禁止写「管培生/储备干部/实习生」、职能类合计不超过 5 个。
2. **比对放到本地代码做**，不再由模型直接判 yes/ask/no：画像里有同方向岗位且岗位名通过通用性校验 → `yes`；画像列不全（岗位数 < 8、业务链条写不出或环节数 < 3）→ `ask`；画像完整但链条上没有学生方向 → `no`。注意这里的 yes/ask/no 是**推断话术的三档**，和第二节企业最终状态的 hit/inferred/miss 不是同一套。
3. **画像按企业缓存、不含意向**——换专业、换意向不用重算，这是「在采集端就先建画像」的前提。画像落在 `data/company_job_profile.json`，谁都能逐家核对。
4. 保留旧路线作为开关：`FAIR_FIT_MODE=bizfit` 走 `biz_fit.py`，默认 `profile` 走新路线。

两条纪律没变：`no` 只表示「这个展位这次别排队」，不等于人家不招；模型不可用/超时/解析失败一律退 `ask`，绝不默认 `no`。

**一个值得记下来的反面实验**：曾加过「跨批出现 ≥45% 的岗位不能单独当 yes 证据」来过滤万金油岗，结果 yes 从 29 家塌到 2 家、ask 涨到 28 家——制造业都设设备/质量/工艺岗是真实共性，不是没信息量；被压成 ask 的里面还有万达商管这种真有电气/暖通岗的。规则撤了，真正该防的「岗位名是编的」交给校验层 `is_generic_title` 挡。

**0 岗企业单独走一条推断链**（`unknown_infer.py`）：未知1（有粗略业务描述）、未知2（联网仍无岗）、以及早期只标「未知」的一批，统一交给模型按学生**当前勾选的意向原词**判断，最多挑 2 个、绝不造新名字、明显不匹配写「无」。这一层刻意**逐家判**（`BATCH=1`）：实测把国联财务和 IT 企业塞进同一批，它会被判成「可能招软件岗」，单独判则是「无」。逐家判用最多 8 个并发发请求，提示词不变，结果与串行逐字一致。缓存键含模型名 + 提示词 + 代码指纹，换模型或改逻辑自动丢弃旧结论。

## 二、命中 / 推断算法改了什么

| 改动 | 改前 → 改后 |
|---|---|
| hit 的判定依据 | 曾按「专业学过什么、具备什么能力」推断对口 → **只看岗位本身**：企业岗位是意向的同义叫法，或日常职责属于同一职能类才算 hit；跨职能一律 miss，共享「管培生/专员/工程师」后缀不算 |
| 代码级兜底 `guard_matches` | 模型会把会计判成供应链、把战略管培生判成供应链管培生 → 确定性剔除财务/战略/数据库/研发/销售/人事/行政七类误判；同时补回漏判的明确同类岗（如「供应链事业群管培生」） |
| 无 JD 企业 | 曾可判 miss → **必须判 inferred**（行业未知除外）；模型第一批漏判的再由 `infer_missing` 按行业补一次推断 |
| 排序 | 曾出现 miss 打高优先级、priority 打到 8 → 钳位 1~5，按「明确命中 > 推断 > 不对口」分组、组内按 priority 降序 |
| inferred 的岗位名 | 旧 `llm_match` 表里有「state=inferred 却带岗位名」的自相矛盾行 → **推断态一律不展示具体岗位名**，原名留在 `original_matched_jobs` 供核对 |
| 命中理由 | 旧理由按别的画像写（常写「学生专业为管理科学与工程」），还会把管培生说成「干的活相近」 → 明确命中改为按对齐后仍存活的岗位重写；推断企业换成与画像无关、只讲证据状态的中性理由 |
| 校招公告「没有就是没有」 | 旧排除只认原始 `state=inferred`，11 家早期按宽口径判成 hit 的企业（普洛药业、比特大陆、古茗、圣奥…）被语义降级后反而带着「建议现场确认是否招 X」出场 → 这条检查**移到语义降级之后**，并明确排除已现场确认招的企业 |
| 展示条数 | 命中岗位只在 JD 前 6 条取交集，排第 12 位的对口岗被整段吞掉 → 按判定结果去重，只截断**显示**，`hit_total` / `miss_total` 记真实条数，页面标「等 N 个」 |
| 共享字误命中 | 食品研发 × 药品研发只共享「研发」也可能被判同族 → 模型复核接口 `/api/fair/verify`，未复核的如实标注 |
| 复核从二分类改三态 | 旧版逼模型在「同类/不同类」二选一，「C++ 开发工程师 × 后端开发工程师」误报（实测精确率 90.9%，40 对里 6 对）→ 增加 0.5「弃权」，用 `3×误报 + 1×漏报` 的代价函数取舍；同时把融合逻辑移出缓存键，改规则不再重问模型（此前命中家数会在 19 / 13 之间跳） |
| 行业简称归一 | 学生意向「控制工程师」、公告写「自控工程师」，两个字核不共享 → **19 家有真实岗位公告的企业全被推成「推断待核实」**。补同义词表：自控/工控/仪控/集控 → 控制，机修/点检 → 设备维修/设备点检 |
| 不带方向的岗位名 | 「工艺工程师」「质量工程师」不知道是哪个方向 → 新增 `dir_hint` 表按企业主营推方向；方向相容照常命中，不相容在「现场问」里说清 |
| 幻觉脱敏（v6） | 模型给出别家的岗位名、或无 JD 却标 hit → 岗位名改成「（待现场确认：XX）」、状态下调 inferred；只拦岗位名和证据等级，**不删企业、不降优先级**，原文留在 `original_*` 供核对 |
| 排序与名次 | 状态组只用于同分并列的先后，**不进名次比较**；分数只衡量城市/性质/规模/行业地位等硬件条件，岗位状态不参与 |
| 分级出榜 | v12 硬约束不满足 + 教培未接受 → 直接删；v15 `llm_match` 明确 `miss` → 删（未知1/未知2 与 0 岗一律保留、不降权）；v17 来源为完整校招公告却无对口岗 → 删 |
| 现场回流 | v7：`fair_feedback` 里「招」把推断升级为明确命中并撤掉推断提问，「不招」顺延到队尾；现场事实优先于模型结论 |

**缓存防串味**：判定缓存的 key 统一为 `md5(缓存名 | 依赖模块 AST 指纹 | 业务参数)`——改注释不失效，改一行逻辑或提示词必失效，失配的自动归档到 `data/_stale_cache/`。两处专门修过的坑：`hit_verify` 只把提示词放进键、融合逻辑读时现算（否则改一次规则就重问模型）；`unknown_infer` / `biz_fit` / `job_profile` 把**模型名**放进键（曾漏掉，换模型后页面写着「大模型判断」，用的还是上一个模型的结论）。

**可信度三层** high / medium / low 只由证据来源决定；低可信的显式标出、可筛选折叠。每次跑 `refresh_all.py` 都会过 parity 一致性测试，Python 与 JS 两边任何一边改词表都会被抓。

## 三、数据库本身改了什么

当前活库 `ent_tools/data/careersafari.db` 实测：

| 表 | 条数 | 存什么 |
|---|---:|---|
| `company_jobs` | 145 | 参会企业主表，`item_json` 是唯一正本；其中 117 家有岗、28 家 0 岗，岗位合计 1,139 条 |
| `company_jobs_prev` | 122 | 换场次时归档的旧企业库 |
| `jd_records` | 118 | 原始 JD 文本、来源、可信度、解析状态；parsed 37 / no_jobs 81 |
| `positions` | 277 | 归一化岗位（含异名、工作场景、来源 JD） |
| `job_evidence` | 662 | 岗位级证据片段与置信度 |
| `job_dir_hint` | 69 | 本地推的岗位方向，报告侧回退用 |
| `llm_match` | 241 | 模型判定 hit / inferred / miss；hit 52 / inferred 85 / miss 104 |
| `cache_meta` | 0 | 缓存指纹登记（实际指纹在 JSON 文件的 `_cg` 字段） |
| `fair_profiles` / `fair_active` | 3 / 1 | 采集端画像 / 当前生效画像 |
| `fair_feedback` / `test_sessions` | 0 / 0 | 现场核实回流 / 测试记录（只追加） |
| `source_snapshots` | 1 | 原网页内容哈希，防「页面变了没发现」 |

结构性改动：

- **表的增删**：原始交接 schema 里的 `users / responses / profiles / requirements` 四张表在当前活库里已经不存在；早期补过两张交接库没有的表 `company_jobs`、`llm_match`（当时灌了 118 家企业、277 条岗位、118 条模型结果）。之后才有换场次归档 `company_jobs_prev`、交付库证据 `job_evidence`、缓存指纹 `cache_meta`。注意 `README.md` 里「122 家 / 762 条岗位 / 8 张表」是旧口径，以实测 145 家 / 1,139 条岗位 / 14 张表为准。
- **v6 写库闭环**：以前页面导出的画像只写浏览器 `localStorage`（`saved:false`），服务端只塞过一条示例画像。新增 `fair_profiles` + `fair_active`，`POST /api/fair/profile` 写库并置生效；`fair_bridge.read_db()` 优先读生效画像，再重建 payload。报告因此读到的确实是学生刚提交的那份，不是生成时的冻结快照。
- **v7** 加 `fair_feedback`，现场核实可回流改证据等级；**v12** 加 `test_sessions`，「填了什么 + 排出了什么」只追加、可单独清理，不混进真人数据。
- **唯一写库点** `save_item(name, patch)`，语义是「合并」不是「覆盖」：这次没找到主营不会冲掉上次找到的那句；已补全字段打 `enriched` 标记，不被采集猜测值覆盖。
- **活库不入库**：仓库只放只读种子 `*.seed`（已清空测试记录），服务首次启动复制成活文件；`git pull` / `checkout` 不会替换一个正被 SQLite 写入的活库——2026-11-15 那样做得到过 `database disk image is malformed`。缓存失配自动归档到 `data/_stale_cache/`，保留最近 6 份可回溯。
- **旧链路隔离**：`load_to_db.py` 读的是另一批 118 家 `companies.json`，跑一次会插进 96 家不相干企业；日常只用 `collect_roster` 那条 145 家展位表的链路。
- **接入方式**：就是 SQLite 单文件，现场拷一个文件即可换数据，**没有数据库服务端**；对外只有 `fair_server.py` 的 HTTP 接口（画像 / 反馈 / payload / 测试记录）和 `portal.py` 的检索接口。活库路径目前只有 `job_store.py` 支持 `FAIR_JOB_DB` 环境变量覆盖，其余脚本仍写死默认路径。

## 四、数据库采集流程怎么改的

```
booths.json（145 家展位表）
   │ collect_roster 自动重建待办快照（丢了不耽误跑）
   ▼
portal.build(name)  联网：多 query 搜索 → 抓页 → 无头渲染 → 选正文
   │ 模型抽岗位 + 主营（biz_scope）；招聘页没写就去「关于我们」补
   │ 失败退规则抽取，不编造
   ▼
save_item → company_jobs.item_json（唯一写库点，合并）
   ▼
_dir_fill.py → job_dir_hint（纯本地，秒级）
   ▼
fair_bridge.build（画像 / 主营判定 / 无岗推断，模型并发 + 指纹缓存）
   ▼
build_fair_page.py → demo/fair.html
```

- **一条命令收口**：`refresh_all.py --collect` 把原来分开的两个入口串成一条，采集完直接重算方向、重建 payload、重建页面、跑一致性测试。以前漏一步的后果是「库里有新企业、报告还是旧的」，而且不报错。现在是 8 步，失败即停。
- **无头渲染从「每次开一个浏览器」改成「一个浏览器开多个标签页」**：冷启动从每页付 1.5~3 秒变成全程一次（约 165 ms）；并发从进程信号量 2 变成标签页信号量 6；单页 5.9 → 2.7 秒，12 页 / 6 线程 25.2 → 11.1 秒。8 个真实招聘页里 7 页正文逐字等长，第 8 页是微信拦截页，两边都拿不到。
- **安全阀**：先走 CDP，返回 `None` 就退回旧的 `--dump-dom`，连续失败 3 次本进程不再尝试；`FAIR_JS_CDP=0` 可强制回旧路径做 A/B。最坏结果等于改动前，不会让采集结果变空。
- **并行边界**：企业之间 6 workers、单家内部最多 6 个 query 并发、模型判定各自线程池、渲染 6 标签页；HTTP 请求总信号量 12。但**抓页面选优仍串行**——它决定「最终选中哪一页」，并行会改变结果。判据是：并行只能改先后，不能改选到什么。
- **断点与增量**：页面正文按企业名缓存 12 小时；没抓到岗位的名单落 `_roster_miss.json`，`--retry-miss` 只重跑它们；`--scope-only` 只补「有岗位但主营为空」；已有 `jobs` 的企业默认跳过（`--force` 覆盖）。
- **外部档案的并入规则**：145 家增补档案优先于 v4.2（后者与参会名单只重叠 22 家），按逐字同名覆盖 6 个打分字段 `city / nature / scale_tier / rank_tier / growth_tier / work_cities`，另有行业地位/成长性证据字段只作展示追加；被覆盖的旧值留在 `_enrich_diff` 可逐条核对。`industry` **不整表覆盖**，只补原值为空/未知的 17 家——增补档案走工商门类口径（风电/光伏→制造），整表覆盖会重演「华为 IT→制造」的错判，档案口径存 `industry_raw`。
- **但要点名当前状态**：`data/fair2026_enrich.db` 现在**并不存在**，所以这条链实际走的是「文件缺失就静默跳过」，当前 payload 里 `enrich_diff_companies = 0`、`rank_cov = 0`。代码接好了不等于数据生效，别把历史效果当成现状。历史接入时实测过：行业地位有档 1 → 35 家、成长性有信号 0 → 29 家、分数区间 21.2~77.5 → 34.0~89.4（见 `V4ENRICH_INTEGRATION.md`）。

## 五、采集端岗位推荐：按五个贴合度层级逐层放宽

不是「推得多」，而是每一层都有明确的用人边界。以自动化专业为例：

| 层级 | 口径 | 实测推荐 |
|---|---|---|
| 1 | 专业和经历匹配 | 电气工程师、电控工程师、自动化工程师、嵌入式硬件工程师 |
| 2 | 专业匹配（忽略经历细节） | 电气设计工程师、PLC 工程师、电控软件/硬件工程师 |
| 3 | 专业不完全匹配但能去、有专业门槛 | 电气运维、仪表、供配电、电气调试、维修工程师 |
| 4 | 专业能去，但很多专业也都能去 | 质量专员、生产计划、采购、技术销售、生产管理管培生 |
| 5 | 和专业几乎无关（教培不限专业的老师等） | 学科教师、课程顾问、教务专员——**只有学生明确接受不限专业才开放** |

配套修正：非计算机/信息大类不再推「软件开发 / 前端 / 后端 / 算法 / 数据开发」，非经管类不再推「管培生 / 储备干部 / 业务运营」，除非实习、竞赛、论文里有实证；相邻层按学科大类分表，不把隔壁专业核心岗（机械设计、结构、仿真）推给自动化；低层已展示的岗位名会喂给模型，换层不重复；模型不可用时规则池兜底，逐层放宽不会空白。

**2026-11-17 补记：推荐口径从「模型想」改成「联网搜」。** 实测模型凭通用认知给岗位名有两个毛病：造词（「运营优化」这类招聘网站搜不到的职能描述）和跑题（与专业关系不大的岗混进池子）。现在的链路（`job_recommend.py`，`PROMPT_VER=rec-v10`）：

1. **先搜后喂**：调 DeepSeek 独立 Search API（`POST /v1/tools/search`，2026-11-13 全家桶开放，同一把 key，5 元/千次）搜「本专业校招岗位」+「所属大类校招岗位」两路，各 8 条，取标题+摘要（`summary` 截 300 字）+来源网站拼证据块注入提示词；证据落盘缓存 6 小时（`data/web_evidence_cache.json`），同一专业几小时内不重复计费。
2. **模型只准从证据里提**：提示词要求岗位叫法取自搜索结果里的写法（可去企业定制括号/年份）、why 必须引用来源、与专业对不上的不提、类别标签不提。
3. **代码落地校验 `_grounded`**：输出岗位名在证据原文里找不到（全名或剥掉职级后缀的核心词都不在）一律丢掉；`_bad_title` 再拦「计算机类岗位 / 信息技术 / 宣讲会」这类公告标签。实测联网模式每次都会拦掉 1～5 个造词。
4. **降级链**：搜索失败/无 key → 纯模型口径（v15 的 prompt）→ 规则池兜底；页面标签区分三种来源——`（联网搜索 · 真实校招口径）` / `（模型生成 · 校招口径）` / `（规则兜底 · 校招口径）`。
5. 岗位名清洗补了分段规则：`Java-校招/实习-北京 → Java-北京`，流程词段（校招/实习/全职…）整段去掉。

**踩过的两条弯路**：① 智谱 `/web_search` 两步走可用，但手头 key 是视觉那把的试用额度，十几次就打空且与 chat 配额同池；② chat 内嵌 `deepseek_web_search` 工具**只有 deepseek-flash 支持**（.env 配的 deepseek-chat 收到 tools 参数会静默忽略——响应正常、没搜过、纯靠知识答，不试不知道），而且**调不调工具模型自主决定**（`tool_choice` 强制实测 400），连发两次都可能懒得搜。独立 Search 接口每次必然返回结果，才改成现在的架构。

### 3. 候选初筛丢岗（`intent_semantics._candidate_titles`）

旧实现按「通用职能词 + 意向相邻二字」打分，**0 分直接丢**：

```python
n = sum(1 for k in keys if k in t)
if n:                      # ← 0 分不进 scored，直接被丢掉
    scored.append((n, t))
return sorted(t for _, t in scored[:limit])   # limit=240
```

两个独立缺陷：

- **量小也筛**：8 个候选只喂 5 个。「公共卫生」的相邻二字是「公共 / 共卫 / 卫生」，`公卫医师` 跨字对不上、又不含 core 词，被丢 → 模型根本没看到这个最对口的岗。

|---|---|---|---|
| 结构工程师 | 25 / **5** | 6 / **0** | 旧逻辑一个对口岗都留不下 |
| EHS安全工程师 | 25 / **12** | 3 / **2** | |
| 原料药质量研究员 | 25 / 10 | 16 / 10 | 持平，但模型判得更全 |

### 4. 三个职能族（`FUNC_FAMILY` + `FAMILY_LABEL`）

`_share_core` 是字面闸门，模型判对但字面零重合的岗会被它否掉。实测误杀：

| 意向 | 被否掉的对口岗 |
|---|---|
| 结构工程师 | 机械设计工程师 / CAE工程师 / 仿真工程师 / 力学分析工程师 |
| EHS安全工程师 | 安环工程师 / 消防工程师 / 环保工程师 / 环境检测工程师 |

### 3. CI 断言从没绿过：构建写 CRLF（`6a2df2d`）

```
.gitattributes:  * text=auto eol=lf      → blob 存 LF
build_fair_page: out.write_text(html, encoding="utf-8")
                 ↑ Windows 上 text 模式按 os.linesep 转成 \r\n
```

CI 链路：`checkout`（autocrlf=false，得到 LF）→ `build`（写出 CRLF）→ `git diff --exit-code` → **必然非空**。

为什么本地没发现：提交时 git 把工作区 CRLF 归一成 LF 存 blob，`git status` 的 `M` 也会被 autocrlf 吞掉；只有「构建」和「diff」在同一个干净检出里连着跑（CI 的做法）才比得出来。

修：三处写盘显式 `newline="\n"`（`fair.html` / `match.html` / `.page_stamp.json`）。

|---|---|
| `head -c 200 demo/fair.html \| od -c` | 0 处 CR |
| `git diff --exit-code -- demo/ ent_tools/data/fair_payload.json` | exit 0 |
| 冷克隆 build 产物 md5 vs 提交版 md5 | 完全一致（fair / match 两个文件） |
| 连续两次 build | md5 不变（幂等） |
| 种子环境 build vs 活库环境 build | 逐字节相同（构建确定性） |

### 4. CI 失败信息可读化

`.github/workflows/ci.yml` 的 diff 步骤从 `git diff --exit-code` 换成 `pwsh` 脚本：用 `git status --porcelain` 列出不一致文件（覆盖面比 `git diff` 更广，含 untracked）、附 `--stat` 摘要、直接给出修复命令。两个分支都本地验过（PASS / 人为改一字节后 FAIL）。

### 5. README 补「克隆后自检」

三条命令 + 预期输出（`pytest` 288 passed / `build` 145 家 / `git status --porcelain` 无输出），并注明第三条就是 CI 的核心断言、有输出该怎么修。

## 补记：名次分层（2026-11-18）

**触发**：人工核对材料科学与工程的榜单，第 1 名是烟台睿创微纳（半导体与集成电路），复检折叠块写着「行业码有限对口（只放通用职能岗）」，`n_blocked=2`——复检自己没确认对口，却排第一。

**根因**：`assemble()` 的排序键把 `-r["score"]` 放在 `0 if r["state"]=="hit"` 之前。分数由 `score_parts()` 算出，三项：城市 34 + 企业类型 23.1 + 行业地位 28.1 = 85.2，**不含任何岗位匹配度**。于是「硬件条件好」在排序上等价于「对口」，与「优先去 / 可以看」的分级（走 `state` / `matched_jobs`）脱节。

**修法**：

```python
_GENERIC_ROLE = ("管培", "培训生", "储备干部", "储干", "储备生", "轮岗", "校招生", "见习")
_UNCERTAIN_CODES = frozenset(["code_edge", "code_out", "biz_other"])

def rank_tier(row):
    js = _row_job_titles(row)
    if js and all(_is_generic_role(t) for t in js):
        return 2                                   # 只看得见管培生
    if recheck_code(row) in _UNCERTAIN_CODES:
        return 1                                   # 复检没确认对口
    return 0                                       # 方向对得上（含推断）
```

`biz_other` 是补进去的：10 份榜单里只有 2 行（法学、新闻的睿创微纳，复检写「主营是别的行业」），但它俩都排在**第 1 位**。`biz_recheck` 里 `biz_other` 本来就在 `DROP_CODES` 中，只是历史原因行没真撤下——既然复检说主营不是这个行业，按同一口径下沉。`biz_weak` / `biz_missing` / `biz_no_word` 暂不并入：当前榜单里 0 次出现，先不扩大范围。

排序键（`rank_sort_key`，顺序即优先级）：

```
feedback=no（现场确认不招） → fit=no 且 via=llm（主营判死） → rank_tier
  → only_ask → -score → state=hit → booth → name
```

**为什么依据是复检码而不是 `state`**：用户明确说「推断有岗命中的正常排……正常的没岗位推断的，和我的方向一致，岗位一致，那就正常排」。`state=inferred` 只说明「没有真实 JD」，不代表「不对口」；天山铝业同样无岗位名但复检判 `code_core`，就该正常排。真正的不确定信号是复检自己给出的 `code_edge` / `code_out`。

**前后端必须同规则**：页面把 rows 拿过去按自己的逻辑再排一遍（`report.js` 两处：默认队列序、`sortMode==='hit'`）。后端改了、前端没改 → 同一家企业前后端名次不同。前端 `fitTier()` 与后端 `rank_tier()` 逐条对应，词表/码表由 `tests/test_rank_tier.py::TestFrontendSameRule` 直接读 `js/report.js` 比对，防止只改一端。

**实测（材料专业画像，42 行）**：

| | 改前 | 改后 |
|---|---|---|
| 睿创微纳（`code_edge`，85.2 分） | 第 1 位 | **第 40 位** |
| 天山铝业（`code_core`，推断无岗位名，85.2 分） | 第 2 位 | **第 1 位** |
| 金田铜业（`code_core`，有实岗「材料研发/生产管理/品质体系」） | 第 3 位 | 第 2 位 |
| tier 0 / 1 / 2 分布 | — | 37 / 3 / 2 |

tier 1 三家：琥崧科技（`code_out`，虽然命中「材料研发工程师」但复检判行业不是这个方向）、沛顿科技（`code_edge`）、睿创微纳（`code_edge`）。tier 2 两家：科伦药业、江中食疗，命中的全是「生产管培生」。

**遗留**：`only_ask` 层仍在 `-score` 之前（既有规则，未动），会出现「80.2 分 only_ask 企业排在 13.2 分企业之后」。是否把该层挪到分数之后，待人工核对后定。

### 一、补库口径第三次收口：没有方向性岗位的一律补

`fill_inferred_jobs.targets()` 的三次变化：

| 版本 | 判据 | 漏掉的情形 |
|---|---|---|
| 第一次 | 清洗后 0 个可用岗位名 | 只有「管培生」的企业算「有岗」，永远不补 |
| 第二次 | `jobSource` 非校招就补 | 校招公告 + 只有管培生，仍然不补 |
| **现在** | 校招公告**且有方向性真实岗**才不补 | — |

```python
_GENERIC = ("管培", "培训生", "储备干部", "储干", "储备生", "轮岗", "校招生", "见习")

def directed_real(o):
    return [t for t in usable_real(o) if not any(g in t for g in _GENERIC)]
```

「只有管培生」不等于「有岗位名」：公告原文写「27届管培生」，学生看不出这家招什么职能，匹配端也无从判断对口。这类企业补一份按主营的推断岗，参与匹配。

**实测**：第 3 次收口命中 3 家 44 条——杰西圈（真实 1 = 管培生）、古茗（真实 9 全是管培生）、中化金茂物业（真实 1 = 向阳生管理培训生）。补完后全库「两头都没有」的企业 **0 家**（非企业主体 17 家已排除）。

### 二、`campus_no_fit` 不能用在「只有管培生」的企业上

补完推断岗，杰西圈/古茗/金茂仍从榜上消失。根因不是补库，是排除规则：

```python
# 改前：校招公告 + 没对上 → 整家排除（前提是公告确实列了方向性岗位）
if prep.state_final == "inferred" and prep.jobs and source_class(...) == "campus":
# 改后：加一道「公告里真的写了方向性岗位」
if (prep.state_final == "inferred" and prep.jobs
        and _has_directed_jobs(prep.jobs)          # 新增
        and source_class(...) == "campus"):
```

`_has_directed_jobs()` 排除管培/储备/见习。只有「管培生」的公告不构成「这家不招这个方向」的证据——清单里根本没有方向可判，按这条排除等于把「信息缺失」当成「不招」。同一判据同步加到 `_drop_campus_unfit()`。

### 三、模型推荐的岗位顺序：按「与本专业 L1 的贴近度」重排

**现象**：采集端填「化学」，推荐第一条是「材料研发工程师」（`mode=llm-web`，缓存在 `job_recommend_pool.json`）。规则兜底给的是「研发工程师、合成研究员、化验/质检岗…」，没有材料。模型把邻专业的岗顶到了首位，而「材料研发工程师」在化学池子里只是 L2。

**修法**：模型返回后做稳定排序，不删不改内容：

```python
def _l1_rank(major, title):
    t = _clean_title(title)
    if t in {_clean_title(x) for x in base_jobs(major)}:   return 3   # 专业专属岗
    if t in {_clean_title(x) for x in core_jobs(major)}:   return 2   # 本专业 L1
    if 专业名头两字 in t:                                   return 1   # 心理测评…
    if 某条 L1 的核心词 in t:                               return 1   # 共享核心词
    return 0

items = sorted(items, key=lambda c: -_l1_rank(major, c["title"]))
```

判据全部是「判断」，**不查 `major_job_pools.json` 那张 93 类的表**：专业专属岗与 L1 来自 `major_l1_authority` 的 `base_jobs` / `core_jobs`，表外专业自动落到「核心词 / 专业名词」两级。实测心理学（不在 93 类池子里）也能排出「心理咨询助理 → 心理教师 → 用户研究员 → 人才测评专员」。

**实测（化学，走在线模型）**：

| | 模型返回顺序 | 重排后 |
|---|---|---|
| 第 1 位 | 材料研发工程师 | **研发工程师** |
| 末位 | 工艺工程师 | 材料研发工程师 |

缓存键 `_pool_key()` 含 `cache_guard.code_fp(name="job_recommend_pool")`，deps 登记了 `job_recommend.py`，所以改完代码旧池自动失效，不会出现「改了排序仍读到旧顺序」。

**测试**：`tests/test_l1_rank.py`（5 条）守住「邻专业岗不得与专属岗同分 / 表外专业判得出 / 重排不删岗位」；`tests/test_inferred_jobs.py::SourceBoundaryTests` 改为「校招 0 岗与只有管培生都要补」。

不让模型写。三个条件缺一不可：跨 ≥3 大类、名字里没写行业（「电气工程师」不加）、
且确实属于该专业的基线岗/大类泛岗（否则计算机的候选会冒出「工艺工程师（互联网/软件）」）。

`title` 始终是提交给匹配端的取值，`display` 只进 chip 与提示文案——否则
「研发工程师（化工/医药）」拿去比企业库的「研发工程师」会对不上。离线规则兜底
（`_jobRecommendRules`）没有后缀，前端按 `display || title` 降级。

## 补记：医药细分产业带（2026-11-18）

用户用「生物」跑了一遍：「他给我推的都是药企业，药企和化学明显对胃，生物的话应该是
生物制药更对胃吧」。查下去不是「药企太多」——库里的 19 家医药本来就该出现——而是
**「医药」在行业枚举里只有一格**，大输液 / 注射剂 / 原料药与疫苗 / 细胞基因治疗拿同一
个行业分，谁的城市与性质分高谁在前。外加两家名字带「生物」的企业（纺织印染助剂、
卫生杀虫剂）靠名字过了主营闸门。

### 一、分带判据（`sector_fit.classify`）

只对 `industry == "医药"` 生效；输入是**主营描述**（`v42.segment` + `biz_scope`），
**企业名不进证据**。这一步是两个刻意的选择：

- 不越权重判行业：别的行业各有各的主营闸门，这里只处理「医药内部不分带」；
- 名字不算证据：多恩（纺织印染助剂）、功成（杀虫剂）就是靠名字里的「生物」进来的。

判定顺序：

1. **试剂 / 体外诊断是决定性证据**（`体外诊断`/`IVD`/`诊断试剂`/`检测试剂`/`试剂盒`/
   `试纸条`/`化学发光`）。上成主营开头写「食品安全」，但真正在卖的是胶体金试剂条，
   按最早出现排会被「食品」抢走，所以这一组先判。
2. 其余按**词在主营里最早出现的位置**定主业（同位置取更长的词）：主营开头往往才是主业。
   华海「仿制药、生物药、创新药」→ 化学药；科伦「大输液」→ 化学药；
   中科开浦「疫苗与细胞基因治疗」→ 生物药；益丰「药品零售…医疗器械」→ 流通。

| 带 | 示例 | 化学的实测依据 |
|---|---|---|
| 生物药 | 中科开浦 | 疫苗、细胞基因治疗 |
| 化学药 | 科伦 / 华海 / 普洛 / 奥翔 / 久安 / 凯瑞斯德 | 输液、仿制药、原料药、制剂、注射剂、手性 |
| 中药 | 华润三九 | 中药、配方颗粒 |
| 器械诊断 | 上成 / 诺尔曼 / 迈科维 | 检测试剂、IVD、神经调控 |
| 医药流通 | 益丰 / 全亿 | 药品零售、连锁药房 |
| 非医药 | 多恩（纺织）/ 功成（杀虫）/ 媛颂（医美）/ 江中食疗（食品） | 主营不是医药这行 |

### 二、专业档位（`sector_fit._PREF`）

只有生物类登记档位，数值小 = 更对胃：

| 专业族 | 生物药 | 器械诊断 | 化学药 / 中药 / 流通 | 非医药 |
|---|---|---|---|---|
| 生物药方向（生物 / 生物技术 / 生物工程 / 生物科学 / 微生物 / 生物制药） | 0 | 1 | 2 | 3 |
| 器械方向（生物医学工程 / 医疗器械 / 医学影像） | 1 | 0 | 2 | 3 |
| 化学 / 药学 / 其他 | 不登记（`rank=None`，等于不参与） | | | |

两处坑写在代码里：`生物医学工程` 含「生物」，必须先于「生物」匹配，否则会被判成生物药
方向；`药学` 不登记档位——原料药与生物药都是它的主场，现有榜单一动就乱。

### 三、落到排序与剔除

- **排序**：`rank_sort_key` 在 `rank_tier`（复检分层）之后、`-score` 之前插入
  `sector_rank`。同一条带先聚在一起，带内才比城市/性质/行业地位攒出来的分数。
  不分带的专业 `sector_rank` 恒为 0，规则与改动前逐字节一致（化学 21 行实测名次未变）。
- **剔除**：生物类专业的行若判成 `非医药` 带，**拼行前撤榜**，进 `biz_fit_no`
  （`{name, why}`），理由写「名字里带「生物」，主营其实是……，不是医药这行」。
  这一条只对生物族生效（`sector_fit.family_of(major)` 为真），化学/药学照旧保留
  ——纺织印染助剂对化工学生是精细化工，对生物学生才是跑题。
- **前后端同源**：`js/report.js` 两处重排（默认队列序、只看命中）都插入
  `(a.sector&&a.sector.rank!=null)?a.sector.rank:0`，`rank_reason` 追加「；细分 …」。
  页面会拿 rows 自己再排一遍，两端不同源就出现「后端第 1、页面第 4」。

### 四、岗位推荐端同步

`industry_tag("生物")` 从「医药/医疗」改「生物制药」（`MAJOR_TAG` 里加了生物族与
生物医学工程两行），于是采集端 chip 显示「研发工程师（生物制药）」，与用户的口径一致；
`title` 仍是提交值，不受影响。

### 五、验证

- `tests/test_sector_fit.py` 23 条：19 家真实企业的分带、非医药行业返回 None、
  生物档位顺序、化学/药学不分带、排序键（63.6 分器械诊断压过 73.5 分化学药）、
  `report.js` 两处排序与名次理由同源。
- 生物画像实测（`/api/fair/preview`）：9 行，第 1 中科开浦（生物药），2–3 器械诊断，
  4–9 化学药与中药；`biz_fit_no` 13 条含多恩 / 功成（名字骗人）与既有 11 条主营不符。
- 化学画像实测：21 行，名次与改动前完全一致（`sector.rank` 全为 None）。
- 全量 `346 passed, 6898 subtests passed`。

## 补记：名单落库与经历对应岗（2026-11-18）

### 一、名单为什么必须落库

企业端导入 132 家后页面写「匹配池共 132 家」，但 `js/match.js` 只有
`localStorage.setItem("companies", …)` 一处写入，**全仓没有一处读回**；匹配端读的是
`/api/fair/payload`。两条链路因此各走各的：

| 链路 | 引擎 | 有主营复检 | 有细分产业带 | 按名单收口 |
|---|---|---|---|---|
| 匹配端（payload → `report.js`） | 服务端 `fair_bridge` | 有 | 有 | 改动前无 |
| 企业端名单池（`match()`） | 浏览器内置一套 | 无 | 无 | 有（仅本页） |

### 二、落库与收口

`roster_store.py`：表 `fair_roster(fair_id, name, note, created_at)`，主键
`(fair_id, name)`。`set_names()` 是**整表替换**——名单是「这一场参会企业」的完整集合，
增量会留下上一场的残名（与 `sync_profile_seed` 清空历史画像同理）。

接口（`fair_server`）：

- `POST /api/fair/roster`：`{names, missing:[{name,note}], rebuild}`；落库后触发
  **后台** `fair_bridge.build()`。这里只 build、不跑 `match_fill`——名单只影响「排谁」，
  不影响「命中结论」，没必要为它再调一遍模型。
- `GET /api/fair/roster`：条数 + 重建状态（`rebuilding/done/error`），前端据此提示。
- `names: []` = 清空，回到全库口径。

`fair_bridge.apply_roster()`（抽成纯函数为了可单测）：

```
rows 过滤到名单内
四个排除清单（hard_filter.dropped / campus_no_fit / biz_fit_no / excluded_*）一起收口
missing = 名单 − 进榜，逐条给原因：
    硬条件剔除 / 校招公告没有对口岗 / 主营不交叉 / 导入时就知道没抓到（城市对不上等）
```

**名单为空时一行不动**：没导入、冷克隆、CI（种子里没有这张表，`get_names()` 吞掉
`no such table` 返回空）都走全库口径，构建产物与改动前逐字节一致。

### 三、实习 / 竞赛 → L1 对应岗

用户口径：「一个文科生干了一个供应链的实习……实习干啥，L1 推啥（干 1 个推一个，
其他的还是专业推，也还在 L1）……竞赛一个数据分析竞赛就推一个（只一个），论文暂时不考虑」。

三层实现（`job_recommend.py`）：

| 函数 | 职责 | 关键点 |
|---|---|---|
| `experience_jobs(cats)` | 实习/竞赛 → 一个通用校招岗名 | `_FUNC_TITLE` 51 条职能词表 + `_COMP_TITLE` 6 条竞赛表；同职能去重，不同职能各一条；论文不参与 |
| `_with_experience(items, exp)` | 插到 L1 池首并打 `_exp/_exp_from` | 同名岗（化学「研发工程师」）就地标记 + 换理由，不重复加；**不过 `_major_ok`** |
| `experience_drop(cats, exp)` | 撤掉同一信号带出来的那批岗 | `SIGNAL_RULES` 一条「供应链」带 4 个岗，一段实习给 4 个会把 L1 撑满 |

排序键从 `-_l1_rank` 改成 `(0 if _exp else 1, -_l1_rank)`：经历岗恒在最前，其余按原
规则。补位的 `seen` 集合也并入 `_edrop`，否则补位会把刚撤掉的信号岗补回来（第一次
实现的漏洞，实测汉语言文学池里又冒出「供应链/计划岗 + 采购专员 + 物流运营岗」）。

为什么必须不过专业闸门：`_major_ok("供应链专员","化学",0)` 为 False——化学的领域词表
里没有供应链。文科生则因为「识别不出领域」被放行，但模型根本想不到给他供应链岗。
经历层兜的正是这一块：**学生亲手干过的事，证据强度高于专业对口**。

层间：经历岗只进 tier0/tier1；tier2 不再重复（L1 已经给过），靠 `tier <= 1` 守。

### 四、验证

- `tests/test_roster.py` 9 条：整表替换、fair_id 隔离、清空、按名单过滤、missing 原因
  （含「导入时就知道的原因」透传）、排除清单同步收口、空名单不动。
- `tests/test_experience_jobs.py` 10 条：文科供应链实习进 L1 第一条、一段一岗、
  两段两岗、同职能去重、竞赛只一个、论文不产岗、「没有/无/跳过」忽略、tier2 不重复、
  五条真实简历文本的映射。
- 接口实测（本机 8102）：名单 3 家 → rows 3；混入不存在的公司 → `in_rank=2`，
  `missing` 写「搜到的公司在深圳，与名单对不上，按没查到处理」；清空 → 回到 9 行。
- 离线规则池实测：汉语言文学＋供应链实习 → `供应链专员(经历) / 语文教师 / 中文编辑 /
  文案策划 / 内容编辑`；化学＋有机合成研发实习 → `研发工程师(经历)` 打头；机械＋PLC
  调试实习 → `电气工程师(经历)` 打头。
- 全量 `364 passed, 1 skipped, 6903 subtests`。
