# 三端技术手册（给接手的开发者）

> 这份文档只回答三个问题：**每一端的输入是什么、输出是什么、中间怎么处理数据。**
> 面向要接手/改动这套代码的人。代码以 `ent_tools/` 为准，行号是撰写时的快照，改代码后请以函数名为准。
> 配套架构图：`docs/架构图.svg`（端到端数据流）。

## 0. 一句话总览

```
采集端（学生画像）──┐
                    ├─→ careersafari.db（SQLite，唯一事实源）──→ 匹配端 ──→ fair_payload.json ──→ fair.html
企业搜索端（岗位库）┘                                            ↑ 现场反馈回流
```

三端不直接互相调用，全部通过 `data/careersafari.db` 和几个派生文件交接。这是整个系统最重要的边界。

| 端 | 输入 | 输出 | 主脚本 |
|---|---|---|---|
| 采集端 | 学生的 6 段对话问卷 + 可选简历 | `fair_profiles` / `fair_active` 表 | `fair_server.py`、`fair_ingest.py`、`resume_parse.py` |
| 企业搜索端 | 145 家企业名单（`booths.json`） | `company_jobs` 等岗位库表 | `collect_roster.py`、`portal.py`、`enrich_by_llm.py` |
| 匹配端 | 生效画像 + 岗位库 + 辅助数据 | `fair_payload.json` → `fair.html` | `fair_bridge.py`、`fair_report_js.py` |

当前数据规模（2026-11-16）：145 家企业，真实岗位 1329 条（其中 892 条带真实来源 URL），大模型推断岗 591 条（单独标注、不进命中证据），校招核实库 90 家 / 615 条全带 URL。

## 1. 采集端：把学生问卷变成一份可打的画像

### 1.1 输入

**前端**：`demo/fair.html`，学生用对话回答约 6 段问题。答案结构见 `blankAnswers()`（`fair.html:1098`）：

- 身份与意向：`identity{name,school,major,degree,...}`、`intended_jobs[]`（意向岗位）、`direction_interest`
- 偏好排序：`city_rank` / `company_type_rank` / `industry_rank`、`tri_weights{7 维}`、`values{salary,stability,...}`
- 条件：`region`、`hard_filter`（自由文本硬条件）、`accept_no_major`
- 简历：可选上传，txt/md/html/docx/图片（**不支持 PDF**）

**入口 API**（`fair_server.py`）：

| 端点 | 作用 |
|---|---|
| `POST /api/fair/profile` | 提交画像：收到 `{document: <完整画像>}` → `fair_ingest.save_profile()` → 后台重算 |
| `POST /api/fair/resume` | 上传简历 → `resume_parse.parse_resume()` |
| `POST /api/fair/feedback` | 现场点「招 / 不招」回流（属于匹配端的输入，见 §3） |

**注意一个坑**：前端 `fetch` 被离线垫片劫持（`fair.html:648`），同源模式下真正 POST 的是完整 `document`，不是原始的 answers。`file://` 双击打开时只写 localStorage、不落库。

### 1.2 输出

落到 `careersafari.db` 三张表（建表在 `fair_ingest.py:34`）：

- `fair_profiles(fair_id, created_at, persona, completeness, document_json)`：所有历史画像，`document_json` 是完整 JSON。
- `fair_active(id='current', fair_id, updated_at)`：**单行指针**，指向当前生效画像。新提交覆盖它。
- `fair_feedback(name, result, note, fair_id, updated_at)`：现场核实回流（匹配端消费）。

派生文件：`data/fair_payload.json`（由后台重算触发 `fair_bridge.build()` 生成，见 §3）。

### 1.3 数据处理

**归一化 `fair_ingest.normalize()`（`fair_ingest.py:76`）**——入口的第一道闸：

1. 非 dict 直接报错；兼容 `{document: doc}` 和裸 `{answers:...}` 两种形态。
2. `setdefault` 补 `document_type / fair_id / generated_at / quality / privacy`；**强制改写** `privacy.storage = "sqlite:fair_profiles"`。
3. **脏意向过滤**：`intended_jobs` 里逐项 `strip()`，丢弃 `None` / 空串 / 纯空格 / 非字符串。这是硬要求——留一个 `None` 会让下游 `"、".join(...)` 崩溃、接口 500、payload 卡在上一个学生（`fair_ingest.py:90` 的注释记录了这次事故）。

**画像生效机制**：写入即覆盖 `fair_active`。`POST profile` 时特意**不**当场重建 payload（`rebuild=False`），而是起后台线程 `_recompute_worker()`（`fair_server.py:81`）：`read_db → profile_from → match_fill.fill(force=True) → fair_bridge.build()`，失败不写半截结论。重算期间 `GET /payload` 返回 `{computing:true}`，前端轮询 `/version` 等结果——防止拿到上一个学生的报告。

**简历解析 `resume_parse.py`**：字段带 `{value, source, evidence}` 三元组便于追溯；教育经历只在前 30 行找、过滤讲座/大赛噪声；手机号归一成 11 位纯数字；抽不到的进 `missing/warnings`，**不编造**。模型失败退回规则。

**必须知道的两个口径**：

- **空意向回退有显式标记**：学生一个意向都不勾时，`profile_from()`（`fair_bridge.py:419`）回退到默认意向 `[供应链计划, 数据分析师, 商业分析]`，同时置 `intents_defaulted=True`，让匹配端知道"这不是学生勾的"，据此把判出的 hit 降级为 inferred（不能冒充明确命中）。
- **权重归一到 100**：`weights_from()`（`fair_bridge.py:444`）以 `answers.tri_weights` 为准，值为 `0` 表示"明确不选"须保留；兼容旧 `values` 字段映射。

**调用链**：

```
fair.html:generateProfile → fetch垫片:_buildDocument → POST /api/fair/profile
→ fair_server.do_POST → fair_ingest.save_profile → normalize → INSERT fair_profiles + fair_active
→ _trigger_recompute（后台线程）→ match_fill.fill(force=True) → fair_bridge.build → fair_payload.json
```

## 2. 企业搜索端：把企业名单变成带证据的岗位库

### 2.1 输入

**名单源头**：`data/booths.json`（145 条，字段 `booth/name/headcount`）。`_roster_todo.json` 只是派生快照，丢了就从展位表重建（`collect_roster.py:146`）。

**采集模式**（`collect_roster.py:125`）：默认跳过已有岗位的企业；`--force` 全量重采；`--limit N` 冒烟；`--names FILE` 指定名单；`--retry-miss` 只重跑 0 岗企业；`--scope-only` 只补主营。

### 2.2 输出

主库 `FAIR_DB`（默认 `data/careersafari.db`，可用环境变量改）里的表：

| 表 | 关键内容 |
|---|---|
| `company_jobs(name, item_json, updated_at)` | 每家一个 JSON blob，含企业属性 + 岗位数组 |
| `job_evidence` | 逐条岗位证据（company, title, source_url, source_type, confidence） |
| `jd_records` / `positions` | JD 原文与归一化岗位定义 |
| `job_dir_hint` | 岗位→方向 的本地规则补全（由 `_dir_fill` 写） |

`company_jobs.item_json` 的主要字段：`id / name / nature / city / industry / biz_scope / jobs[] / jobSource / jobEvidence / source / date / note`。

**岗位对象**分两类，字段必须分清：

- 真实岗：`title / requirements / headcount / urgency / group / salary / source_url`
- 推断岗：在上面基础上多 4 个标注 —— `job_source_kind="大模型推断"`、`job_profile_basis`、`strength`，且 `source_url=""`（空，绝不冒充真实 JD）

### 2.3 数据处理

**完整链路**（`collect_roster.py:204` → `portal.py:981`）：

```
work(name) → portal.build(name)
  ├─ pages_for：先查页面缓存（TTL 12h）→ 未命中才搜
  │    ├─ brand_names 生成 3 个搜索变体 × ("校园招聘"/"招聘") = 最多 6 个 query，6 线程并发
  │    ├─ zh_search.search：Bing 优先，召回不足用 360 补；Bing 对中文长名退化时会被相关度过滤掉
  │    ├─ fetch → strip_html；JS 页走 cdp.render（常驻 Edge、多标签复用），失败退回一次性 dump-dom
  │    └─ page_matches 逐页认领企业（全称/短名强匹配；聚合站额外要求出现招聘词）
  ├─ 模型路径：enrich.call_model → build_entry 抽岗位 → 逐岗回填 source_url → 证据校验
  └─ 规则兜底：extract_jobs（模型不可用/402 时用）
  → save_item 增量合并 → 写 company_jobs
```

**四个必须写明的口径**：

1. **逐岗 URL 回填**：岗位从哪一页抽出，就把该页 URL 贴到每个岗位的 `source_url`；只认 `http` 开头，抓不到留空、**绝不编 URL**（`enrich_by_llm.py:236`、`portal.py:1039`）。这是之前"很多岗无 URL"的根治点。
2. **MISS 不冲空**：本次抓到 0 岗但旧库有岗时，`save_item`（`collect_roster.py:86`）弹掉 `jobs/jobSource/jobEvidence/source` 不写，保住已核对的岗位——之前全量重采把 96 家冲成 0 岗就是这里漏了。
3. **HIT 增量合并**：按 `_title_key`（去空白、括号归一）合并——同名岗用本次带 URL 的新岗顶替，旧库独有的保留；**只增不减**。
4. **已富集属性不被猜值覆盖**：`old.enriched` 为真且本次没有 `enriched` 时，弹掉 11 个属性字段，不用采集的猜测覆盖核实过的属性。

**校招核实库已停用（2026-11-18）**：`campus_recheck.db` 与 `build_campus_recheck.py` 下线，文件存档在 `ent_tools/data/archive/_campus_recheck_retired_20261118/`。停用原因是它给来源做二次判定，副作用大于收益：①`is_campus=1` 的 90 家里 51 家的岗位被整表替换，江苏东成 60 个岗页面只剩 7 个；②11 家活库标「校招公告」的因「没抓到带 URL 的证据」被降级 websearch，绕过「校招没命中直接排除」，睿创微纳 63 个岗还挂着现场提问。**现在一律以活库 `company_jobs.jobSource` 为准，不再有第二套来源标签。**

**推断岗补库 `fill_inferred_jobs.py`**：对**所有非校招来源**（websearch / 社招信息 / 未知）的企业用 `job_profile` 大模型按主营列岗位（**不带学生意向**），转成带标注的推断岗追加进库；真实岗一条不改，同名跳过。2026-11-18 用户定口径：有 20 个对口真实岗也照补，因为推断岗只是补缺口；校招公告来源一律不补。排除非企业主体（学校 / 政府 / 研究所）。开关 `FAIR_INFER_FILL=0` 可关。岗位方向补全 `_dir_fill.py` 是**纯本地规则**，不用大模型。

**环境变量**：`FAIR_DB`（主库路径）、`FAIR_JOB_DB`（页面端读库）、`FAIR_JS_RENDER`（批量采集强制开）、`FAIR_JS_CDP`（=0 退回一次性渲染）、`FAIR_JS_TABS`（并发标签页，默认 6）、`FAIR_PAGE_CACHE_TTL`（12h）、`FAIR_INFER_FILL`、`FAIR_DEMO_RECHECK`。

## 3. 匹配端：把画像 × 岗位库变成一张排行榜

### 3.1 输入

`fair_bridge.build()`（`fair_bridge.py:1433`）读取：

- 生效画像：`read_db()`（`fair_bridge.py:368`）优先按 `fair_active` 指向取 `fair_profiles`，无则取最新一条。
- 岗位库：`company_jobs`（直接按 `jobSource` 判定来源，2026-11-18 起不再二次核实覆盖）、`llm_match`（模型预判定）、`fair_feedback`（现场回流）。
- 辅助数据：`fair2026_enrich.db` 的 145 家增补档案、`v42_company_match.db`、`booths.json`、`job_dir_hint`、`data/test_users/*.json`（内置画像意向，只用于把语义映射一次跑全）。
- JSON/DB 缓存：`hit_verdicts.json`、`intent_semantics_cache.json` 等，都带代码指纹，代码一改自动判失效（`cache_guard`）。

### 3.2 输出

`data/fair_payload.json`（顶层结构见 `fair_bridge.py:1799`）：

- 顶层：`version / generated_at / profile / weights / active_fair_id / hard_filter / campus_no_fit / stats / intent_semantics / hit_verdicts / rows[]`
- 每个 `row` 的关键字段：
  - 状态排序：`state`（`hit` / `inferred`，`miss` 已在过滤阶段删除）、`original_state`、`reason`、`score / rank / rank_reason`
  - 命中证据：`matched_jobs`（仅 hit 有值）、`hits / misses / hit_total / job_titles / evidence{source,date,jobSource,jobEvidence}`、`dropped_jobs`
  - 推断与判定：`fit`（yes/ask/no）、`biz_fit`、`gaps / questions / verify_question`、`infer_notice`、`inferred_jobs / inferred_job_notice`
  - 审计：`dims / parts / trust / guard / feedback / v42 / enrich_diff`

`build_fair_page.py` 把 payload 内嵌进 `demo/fair.html`（约 1MB）——所以**改了 payload 必须重新生成页面**才看得到。

### 3.3 数据处理与算法

**（1）七维加权打分** `score_parts()`（`fair_bridge.py:522`）：

维度 `city=18, home=14, company_type=16, industry=14, scale=14, industry_status=12, growth=12`（合计 100，权重来自画像 `tri_weights`，归一到 100）。每维按画像偏好算 0~1 的值：`city` 取所有工作城市中用户排名最靠前者、`home` 同城 1.0/同省 0.8/邻省 0.6/其他 0.3、其余按企业客观档位表。公式 `score = Σ(weight/total × value × 100)`，漏维按 0 计入、不放大。**分数不含 state**——可信度、待核实一律不进分数。

**（2）三态判定与复核**——这是匹配端的核心：

- 原始 `state` 来自 `llm_match`（模型预判）。`_evidence()`（`fair_bridge.py:1288`）用**企业真实岗位名**重写：`real`（来自 `_clean_jobs()` 的真实 JD）非空 → 升 hit；对齐后无 real 或幻觉修正 → 降 inferred。
- 岗位名语义对齐 `intent_semantics.pair_verdict()` 返回 `ok / ask / no`；`hit_verify` 再对候选对批量复核，返回 `1`（确认同类，可作证据）/ `0.5`（**弃权**）/ `0`（否决）。
- **0.5 的处理是重点**：不算命中证据，但**也不是否决**——不删该岗、不写成"不同职能"，转成一条 `kind="abstain"` 的现场待问，并从 `dropped_jobs` 摘除。代价函数 `Cost = 3×FP + 1×FN`，宁可多问不可错杀。
- 模型不可用时：`hit_verdicts` 空表 → 标"未复核"、退回本地规则，不编结论。

**（3）三道过滤**（打分前）：硬约束 `hard_filter`（不满足即从名单删除，清单进 `hard_filter.dropped` 公示）→ `drop_miss`（只删 `llm_match.state='miss'` 的；**0 岗和未知来源一律保留**，红线"没查到 ≠ 不招"）→ 校招职位不匹配（来源是完整校招公告却无对口岗的，按"公告没有就是没有"排除，现场已确认招的不排除）。

**（4）推断岗只提示、不进命中证据**：`_clean_jobs()`（`fair_bridge.py:34`）排除 `job_source_kind=="大模型推断"` 的岗，使其不进真实 JD、不触发 hit；`_inferred_jobs()` 单独提取，只写进 row 的 `inferred_jobs / inferred_job_notice`。判定 `real` 时对补过推断岗的企业**不放宽**——防止"模型猜的岗"冒充真实 JD 把 inferred 升成 hit（这个口子之前出过 bug，已有测试钉住）。

**（5）现场反馈回流**：现场点「招」→ inferred 升 hit、可信度抬档；点「不招」→ 排序顺延队尾。排序键（`fair_bridge.py:1763`）：第一顺位 `feedback=='no'`、第二顺位 `fit=='no'`，其余只看 `-score`（hit 优先 → 展位号 → 名称）。前端 `fair_report_js.py` 的 `recompute()` 用同一套规则重算，前后端由 `_test_parity.js` 守护一致性。

### 3.4 核心立场（改动时不要破坏）

1. **不做黑箱排序**：名次只由可复算的 `score` 决定；state、可信度、待核实都不进分数。唯一例外是现场确认不招 / fit=no 顺延队尾。
2. **删除必公示**：所有被排除的企业清单（`hard_filter.dropped` / `excluded_miss` / `excluded_campus` / `campus_no_fit`）都进 payload，页面明示，不静默丢弃。
3. **不编结论**：没证据就标"现场问"，不把推断写成事实；推断文案必须写"模型据此认为"。
4. **原文可追溯**：幻觉脱敏/降级保留 `original_matched_jobs / original_state`，可回溯改前是什么。

**调用链**：

```
refresh_all.py → fill_inferred_jobs → _dir_fill → fair_bridge.build → build_fair_page → fair.html
build() 内部：cache_guard.purge_invalid → read_db → load_* → _merge_sources → profile_from
→ 三道过滤 → build_map/ verdicts → weights_from → 逐企业 _evidence/_questions/_hits_and_misses
→ rows.sort → rank → json.dump(OUT)
```

## 4. 改动时的硬性纪律（血泪版）

- **重采对比**：先 `cp careersafari.db xxx.db`，用 `FAIR_DB=<新库>` 跑，绝不直接写活库；只有新库核心指标全部占优才替换。
- **活库不是 git 正本**：正在被 SQLite 写入时 `git checkout/stash/pull` 替换活库会得到 `database disk image is malformed`。发布走 `sync_repo.py --apply`，种子库 `careersafari.db.seed` 才是正本。
- **单实例**：启动前 `_already_serving()` 探测端口；Windows `SO_REUSEADDR` 允许两个进程绑同一端口，会随机打到旧代码，表现成"改了不生效"。
- **测试数据不能污染**：`test_sessions` 是只追加实验日志，刻意不提供一键清空；三套测试画像 `data/test_users/u*.json` 只用于语义映射一次跑全，不进学生真实画像。
- **改完必跑**：`python -m unittest discover -s tests`（当前 88 例）+ `refresh_all.py`（重建 payload + 页面 + 前后端 parity 测试）。

## 5. 代码体检结论（2026-11-16）

给接手的人一个诚实判断：这套代码**不是屎山**，但也不是教科书，属于「边界清楚、局部有历史包袱」的维护型项目。

**支撑「不是屎山」的客观事实**：

- 三端边界清晰，靠 DB/文件交接而非互相调用——这是最重要的架构优点，改一端不容易炸另外两端。
- 有 88 个单测、前后端 parity 测试、缓存代码指纹、幻觉拦截、删除公示等一整套防劣化机制；`build()` 已从 736 行拆到多个 `_xxx` 子函数。
- 判定链可复算、不搞黑箱：分数是加权和，模型只做「读语义 / 写人话」，且模型不可用时明确降级不编结论。

**残留的客观问题（按严重度）**：

| 问题 | 数据 | 判断 |
|---|---|---|
| `fair_bridge.build()` 仍然偏长 | 469 行（曾拆到 443，后续改动又长回） | 最该盯的点。再往里加逻辑前先拆 |
| `except: pass` 静默降级 | 37 处 | 多数是缓存读失败退回重算（可接受），但**统一缺日志**——排查时看不见降级 |
| 同名不同义的 `load_env` | `llm.py` 返回 dict，`enrich_by_llm.py` 写 `os.environ` | 改一个不懂另一个，是典型「改一处坏一处」隐患 |
