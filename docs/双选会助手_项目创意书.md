# 双选会助手（CareerSafari）项目创意书

> 版本：2026-11-14（v0.6）
> 当前系统：145 家仙林专场名单 / 1135 条岗位 / 统一入口 `http://127.0.0.1:8103/`
> 一句话：**名单晚到是结构性的（本项目这场只有 41 小时），所以把耗时的部分放在会前——开发者拿到名单后提前搜索、导入数据库；学生打开页面填完画像，到拿到排序不超过 5 分钟。**

---

## 一、项目一句话定位

一个面向校招双选会的**会前极速规划 + 现场导逛 + 现场回流**工具。核心不是"哪家企业好"，而是"按我自己的尺子，今天下午这三个半小时该先去哪几家"——用逐字段带证据的企业档案和一套可解释的固定打分表，替代现场靠队短、靠名字熟的随机决策。

## 二、核心概念：从「一张名单」到「一条动线」

传统双选会给学生的是一张按展位号排的企业名单（谁在哪个摊位）。但"名单"不等于"计划"：

- 名单是**校方视角**（展位号、单位全称、招聘人数），不是学生视角（这家招不招我的方向、在不在我想去的城市、值不值得排 20 分钟队）；
- 名单在会前 2–4 天才定稿，学生拿到时已经来不及逐家查；
- 名单里没有"今天实际招什么岗"，岗位信息贴在展板上，只能到了现场才知道。

我们追求的是把名单变成**按分数排序的、带展位动线的、每家都能点开看依据的行动清单**。分数只回答一件事：在有限时间里，先去谁那儿。

## 三、目标用户与核心痛点

| 项 | 内容 |
|---|---|
| 主用户 | 研三 / 大四应届生：新到一场双选会，只有 3.5 小时、几百家企业、几十份简历 |
| 次用户 | 高校就业办 / 主办方：名单、展位号、现场核实结果可沉淀成下一届底表 |
| 使用时机 | **名单公布当晚 ~ 会前 1 小时**填画像、出排序；现场按动线走；边问边回流 |

### 3.1 核心痛点：准备窗口只有几十小时

**10 场校级双选会里 7 场的学生准备窗口不超过 48 小时，最短只有 20 小时**；两所 985 巧合地都是 41 小时。扣掉睡眠与上课，41 小时里真正能用来查企业、改简历的不过十来个小时。而企业侧提前 10–45 天就拿到了邀请函——这个落差就是产品存在的理由。

名单发布时刻取自微信公众号推文标题下方的发布时间，或校方页面明写的名单公布日；每场都核到推文正文里的展位表 / 参会单位名录，来源见文末证据清单。

#### 调研方法

1. 进学校就业公众号 / 就业网，找该校**校级、展位最多**的一场双选会；
2. 先读「用人单位邀请函」——发得早，只有报名截止、展位数与费用，不含最终名单；
3. 再找面向学生的推文。它不一定叫「同学邀请函」，标题可能是「4 万岗位等你来」「秋招双选会安排抢先看」「岗位直推」；**判定标准是正文里有没有成串的参会单位名录或展位表**；
4. 用推文发布时间减去开会时刻，就是学生真实准备窗口；
5. 两封邀请函之间的落差，构成信息不对称的时间结构：企业侧提前 10–45 天，学生侧只剩几十小时。

**报名侧时间线同样能说明问题**：11/15 仙林场 11/3 企业函 → **11/10 报名截止** → 11/13 名单 → 11/15 开会；11/14 文理场 9/28 企业函 → 11/8 截止 → 11/12 名单 → 11/14 开会。**名单只能在报名截止、确认最终到场单位之后定稿**，窗口被结构性压到最后两天，且常常是晚上收到一个 xlsx。

### 3.2 为什么名单必然越晚越精确（机制，不只是猜测）

邀请函条款里有直接证据：

1. **报名 ≠ 到场**：南大邀请函写「名额报满后将自动停止报名」「学校有权对不符合相关规定的招聘信息和活动进行**调整、暂停或取消**」；南航 11/19 专场的企业邀请函更直接——「通过审核的单位请按时参会，**无故临时取消将会影响后续入校招聘资格**」（[南航邀请函](https://my.yingjiesheng.com/xjh-006-332-640.html)）。学校要用资格约束来治「最后不来」，正说明这是常态而非意外。企业临时退出、资质复核不过、行程变更都会让名单缩水。
2. **展位号要等名单定稿才能排**：学生拿到的是「展位表」，不是「单位列表」；一个单位变动会牵动整张表的编号。
3. **组团专区整体进出**：东大那场中建集团一家带 60 余家下属企业、宁波/常州/芜湖人社专区、南大 11/14 的鄂尔多斯专区（展位 90–97）都是成块变动。
4. **数字最后一刻才收敛**：11/13 同学邀请函写「近 150 家用人单位」，最终展位表实际 **145 家**。
5. **展位号本来就是最后才定的**：第三方会务邀请函把「**会前三天发入场通知书给参会单位（含展位号、入校报备）**」写进参会流程（[南京硕博巡回双选会邀请函](http://mp.weixin.qq.com/s?__biz=Mzk0NTY5MjcwMA==&mid=2247484853&idx=1&sn=7f7c8766264fcd71795dd16820e8f058)）；南航 11/19 也要求企业「**活动前一天**」才提交入校申请。展位表要等这些确认齐了才能排。

6. **连展位号都能拖到当天**：江苏经贸职业技术学院 11/18 通知写「用人单位展位以**活动当天现场布置为准**」「逾期未办理报到手续，展位 13:20 自动取消」；三江学院 11/20 两院专场把展位预定截止设到 11/15 17:00，并要求「不能到会提前 3 天告知」；南京农业大学 11/21 写「展位号以最终通知为准」；南京邮电大学则写明「无故缺席将被列入招聘单位失信名单」。**学校越晚发越准，是流程设计出来的，不是效率问题。**

结论：早发名单会误导学生，晚发才准。这不是学校效率问题，是**精确性与准备时间之间的硬取舍**。所以产品价值不该定位在"提前很久慢慢查"，而应定位在**名单落地后的极速处理**——把 T+2 天压缩成 T+几十分钟。


### 3.3 拿到名单之后，学生还卡在三道关

| 障碍 | 具体表现 |
|---|---|
| 信息不对称 | 名单只有单位名 / 展位号 / 招聘人数，没有今年招什么岗、什么性质、在哪个城市、规模多大 |
| 决策无依据 | 投递顺序靠"哪个队短""哪个名字熟"，逛完才发现最该去的那家没去 |
| 通用大模型帮不上 | 把简历 + 名单一起喂模型排序：① 不熟的企业会错填（实测把外企填成民企、IT 填成制造）；② 标准飘在提示词里，每次结果不同、说不清理由；③ 产出是会过期的聊天文字，不能筛选、不能重算、不能现场回流 |

补充一个容易被忽略的对照：学校侧已有类似尝试——东南大学 2026 春季推出「名师英才职通车」，学生**扫码签到后**录入专业/学历/求职意向，系统生成专属岗位清单并提供展位导航（[报道](https://m.toutiao.com/article/7702384310665413146)）。它是**现场、校方统一口径**；我们做的是**会前、学生自己的尺子、逐字段带证据 URL**。两者不冲突，反而说明"展位领航"是已被验证的需求。

## 四、主打功能

1. **名单极速入库**：一个 xlsx 展位表 → 145 家企业、展位号、招聘人数自动导入；旧名单自动备份不丢。
2. **逐家建企业档案**：联网核验校招公告 / 高校就业网 / 企业官网 / 公众号，抽岗位、城市、性质、行业、规模档，**每条事实带 source_url**（本项目已接入 662 条字段级证据）。
3. **AI 读简历 + 会前画像**：照片 / txt / md / docx / html 简历真实识别（图片走视觉模型 OCR），1 分钟问卷收专业、实习/竞赛/论文、意向岗位、七维权重、硬约束、教培接受度。
4. **按学生的尺子排序**：七维固定打分，每条分有 `basis` 可点开；权重可现场微调，换画像即重算，结果可复现。
5. **校招岗位推荐 + 逐层放宽**：先按专业 + 实习 + 竞赛 + 论文给最贴切的岗位；点「换一批」看完自动放宽到专业 → 专业大类 → 不限专业（是否开放教培层取决于学生刚才的回答）。
6. **两页式报告 + 展位动线**：列表页两行摘要 + 「按排名 / 按展位排行」；详情页给算分依据、信息缺口、现场提问、证据溯源。
7. **硬约束与教培开关**：「只要南京」「只看互联网」由模型解析后直接剔除企业；「是否接受教培等无专业要求企业」由学生决定。
8. **现场核实回写（「回流」）**：在展位问到「这家今年招不招这个岗」→ 点一下「招 / 不招」写回数据库；该企业顺延到队尾但不删除、证据等级被修正、下一位同学和下一场双选会直接复用。这是**会后可选的增量动作**，学生不用等它，也不影响秒出结果。
9. **测试记录页**：每次跑保存「填了什么 + 排出了什么」，可查看、逐条删除、批量清理测试脏数据，只留真人记录。

## 五、实现逻辑（三步 + 动态演进）

![产品逻辑闭环：名单落地到现场核实回写](figures/fig2_product_loop.png)

> 先看图：整条链路是「名单落地 → 建档案 → 排序导逛 → 现场核实回写 → 修正档案」的闭环，不是一次性报告。

> **两条时间线**：
>
> | | 谁在做 | 什么时候 | 耗时 |
> |---|---|---|---|
> | **开发者 / 运营侧** | 我们（学生不参与、也不等待） | 拿到企业名单后，会前提前并行搜索、导入数据库、生成企业档案与画像底表 | 本项目实测约 **84 分钟**（11/13 晚拿到 xlsx → 首轮 145 家采集 37 分钟 → 属性 / 证据 / 匹配结论补齐 → 00:21 建库完成） |
> | **用户侧** | 学生 | 打开页面 → 填 1 分钟画像 → 出排序 → 按动线逛会 | **≤5 分钟，结果秒出** |
>
> 学生打开页面时，145 家企业的档案已经在库里了；**84 分钟发生在会前，不占用学生一秒钟**。产品要压缩的指标是用户侧的 ≤5 分钟，而不是让学生等采集。

### 第一步：收数据（名单落地当晚）

- 输入端 A：展位表 xlsx → 企业全称 / 展位号 / 招聘人数；
- 输入端 B：企业侧公开信息（校招官网、高校就业网、公众号、企业库、主流招聘平台）；即便单次召回量很少也保留该来源，避免漏掉只在单一平台发布岗位的企业；
- 输入端 C：学生侧简历 + 问卷（专业、实习 / 竞赛 / 论文、意向岗位、权重、硬约束、教培）。

> 本项目实测：11/13 晚拿到 xlsx → 当晚完成 145 家导入与首轮全量采集（约 37 分钟），14 日上午完成补齐与建库，15 日下午会场前即可用。**这条时间线就是产品的核心指标。**

### 第二步：建档案（把"名单"变成"事实表"）

- 每家企业、每个字段单独存证据 URL，能回溯到发布方原页；
- 口径纪律：行业按**主营 / 招聘口径**判定，绝不抄工商门类；`0 岗` 标「没查到」，**不等于「不招」**；
- 不确定就写「未知」，模型补全失败退回规则而不是编；
- 规模档等缺失字段由 `classify_scale` 推档，但不空档、不编造。

当前底表：**145 家 / 1135 条岗位 / 123 家有岗 / 22 家 0 岗**；22 家 0 岗里党政机关 8、学校 6、教培 1，**真企业只剩 7 家**。

### 第三步：按学生的尺子排序 → 导逛 → 回流

- `calcOne()` 七维：城市 / 离家近 / 企业类型 / 行业 / 企业规模档 / 行业地位 / 成长性，权重来自学生填的 100 分；
- 岗位数量、岗位类型、薪资**都不进分数**；低置信度 / 需现场核实只作展示标注，**不影响排名**；
- 大模型只做三件可控的事：岗位语义判定、校招岗位候选生成、联网补全，**不碰打分**；
- 现场核实回写（即「回流」）：学生在展位确认「招 / 不招」后写库 → 重建 payload → 队列顺延，形成闭环。**它是可选的会后动作**：不回写也能正常出报告、正常逛会，回写只是让下一个同学和下一场更准。

### 动态需求演进

| 场景 | 系统怎么动 |
|---|---|
| 临时改主意（想离家近 / 想换城市） | 权重微调按钮实时重算，不必重填问卷 |
| 推荐岗位看不上 | 「换一批」逐层放宽：专业+经历 → 专业 → 专业大类 → 不限专业（教培受开关控制） |
| 现场发现企业不招 / 临时换展位 | 回流写库、顺延队尾；展位模式按序号重排 |
| 名单最后一刻又改了 | 只换 `booths.json` + 重跑 build，页面骨架不动 |
| 冷启动（没有历史画像） | 默认七维权重 + 规则推荐兜底，照样能出一份报告 |

## 附录 A 关键机制与诚实性设计

- **打分 v11 七维**：城市（7 类排名）/ 离家近（同城 1.0、同省 0.8、邻省 0.6、其他 0.3）/ 企业类型（国央企·民企·外企三档）/ 行业（对口是硬约束）/ 企业规模档（客观分档）/ 行业地位 / 成长性。权重合计 100，由学生填。
- **未知不计分母**：页面显示"生效权重 %"，不与权重结构不同的企业硬比。
- **大模型边界**：只做岗位语义判定、校招岗位候选生成、联网补全；`score` 由固定公式算，模型不参与。
- **语义岗位匹配**：逐个意向岗位用模型从企业真实岗位名里挑同类，命中显示「企业岗位 X ↔ 你选的 Y」；宁少勿滥。
- **诚实性红线**：`0 岗` = 没查到 ≠ 不招；不臆造岗位名 / URL / USCC；幻觉岗位名拦截并脱敏；现场确认不招的企业顺延队尾但保留；报告明写「分值只用于排序，不代表企业好坏」。
- **教培口径**：岗位内容 + 名称判定，默认剔除；学生明确接受才纳入；`inferred_jobs` 是规则建议，不并入事实岗位、不计岗位数、不进打分。

## 附录 C 技术选型、风险与边界

| 层 | 选型 | 理由 |
|---|---|---|
| 服务 | Python 标准库 `http.server`（单端口 8103） | 零依赖、现场可离线跑 |
| 存储 | SQLite（活库 + 备份 + 证据表） | 单文件、可备份回滚、逐字段可审计 |
| 前端 | 单页 HTML + 原生 JS，统一入口 iframe 三标签 | 双击 `file://` 可用，同源自动切在线写库 |
| 模型 | 智谱 GLM-4-flash / GLM-4V-flash（`.env`） | 语义判定、岗位候选、图片 OCR、联网补全；失败一律规则兜底 |
| 取数 | `fetch('/api/fair/payload')` 动态拉 | 改数据只需 build，不必重新生成 HTML |

| 风险 | 应对 |
|---|---|
| 名单最后一刻变动 | 只换 booths + 重跑 build；现场回流兜底；不删企业只顺延 |
| 口径混用（工商 vs 招聘） | 逐字段映射并审核差异，不整表覆盖 |
| 岗位覆盖不全 | 多来源 + 诚实标注 0 岗 + 语义推断；0 岗不排除 |
| 模型误判 / 超时 | 缓存 + 沿用上次判定 + 规则兜底；短调用避免长超时 |
| 分数被误读成企业好坏 | 页面显式声明「只用于排序」 |
| 登录态平台抓取合规 | 只读列表、真人节奏、失败即停；以公开校招公告为主 |
| 现场照片 / 访谈隐私 | 口头同意 + 人脸 / 姓名 / 手机号打码，见 6.4 |
