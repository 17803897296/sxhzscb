# 修复方案：泛意向岗位要「附和方向」+ 前后端不打架 + 选项去校招字眼

日期：2026-11-16 深夜。起因：用户手测报告「研发工程师 ↔ C++研发工程师 / 自动化工程师 /
电控硬件工程师 / 人工智能算法工程师 ↔ 运动控制算法工程师」这些命中全有问题，
并明确要求：**用户的宽泛选择岗位也应该附和方向——选了「研发工程师」，不能老配上
编程方面的研发**。

## 一、根因（已复现坐实）

用 `python -c` 跑 pair_verdict 复现，意向「研发工程师」与下列岗位全部返回 "ok"（硬命中）：

| 岗位 | 判定 | 走的路径 |
|---|---|---|
| C++研发工程师 | ok | 意向剥中性词后方向核为空 → `not a` 兜底；族表认不出「研发工程师」（刻意不收）→ 不跨职能 |
| 自动化工程师 | ok | 同上 |
| 电控硬件工程师 | ok | 同上 |
| 药品研发工程师 / 后端 / 前端 / 嵌入式 | ok | 同上，洪水就此形成 |

第二类：两个**具体**岗共享动作核但领域限定不同——
「人工智能算法工程师 × 运动控制算法工程师」：方向核 `人工智能算法` vs `运动控制算法`
互不包含，但 DIR_WORDS 都命中「算法」→ 并列方向判据不触发；PROF_DIR 交集 {算法}
非空 → ③ 不拦；族表都是 algo → 兜底放行 ok。

一句话：**泛意向没有任何方向约束，具体岗之间只靠「共享动作词」就能互相命中。**

## 二、修法（三端同源：intent_semantics.py ↔ fair_report_js.py 逐条镜像）

### R1 · pair_verdict / miPairVerdict：泛研发意向 × 带方向岗位 → ask（现场问）
- 判定：意向是「只说了研发/开发、没限定方向」的笼统名（复用 `_soft_broad`，剥掉
  `_SOFT_WIDE` 后为空）且岗位方向核非空（岗位名自己带了方向限定，如 C++研发/
  自动化/电控硬件）→ 返回 **"ask"**，不再 ok。
- 保持不变：岗位名同样泛（b.t 空：「软件研发工程师」「研发工程师」同名/同类）→ ok；
  意向本身带方向的原逻辑一概不动。
- 放在 `if not a` 分支**之前**拦截。文案走 `_ask_why_spec`：现场问一句
  「这个岗具体做哪个方向的研发」。
- 为什么不是 "no"：机器人公司的「研发工程师」真可能就是自动化研发，说「不同职能」
  是撒谎；ask（现场问）才是诚实答案。

### R2 · align_jobs_detail：用户方向域兜住泛意向（Python 侧，后端裁决）
- `_intent_dirs(it, intended)` 已实现「学生勾的其它意向推方向域」。R1 判 ask 后，
  若岗位方向（`job_direction.title_dir(t)`）与学生方向域**相容**
  （`job_direction.compatible`）→ 升回 kept（命中），并在 dir_notes 写明
  「按你的机械方向对上这家机械研发岗」。
- 学生没勾任何带方向的意向（方向域为空）→ 保持 ask，不替学生做主。
- 岗名带方向但 `title_dir` 认不出（C++研发工程师）→ 保持 ask，现场问。
- 此条**只改 Python 后端**，结果经 R4 写进 payload，前端采信后端。

### R3 · pair_verdict / miPairVerdict：共享动作核 + 不同领域限定词 → no
- 判定：两方向核**都以同一动作词结尾**（首期只收「算法」），去掉动作词后的领域
  限定词都非空、互不包含（先过 AI 同义归一：ai ≡ 人工智能）→ 返回 "no"（并列领域）。
- 覆盖：人工智能算法 × 运动控制算法 → no；推荐算法 × 图像算法 → no。
- 不误伤：算法工程师 × AI算法研究工程师（一侧无限定词，走原有 ask→same_dir 命中）；
  ai算法 × 机器学习算法经同义归一后 ai≡人工智能，仍互不包含 → no（不同子方向，
  判 no 是对的）。

### R4 · 后端判定写进 payload，前端采信（消除前后端打架）
- fair_bridge 每家企业 payload 增加 `intent_matches_backend`：
  `[{intent, job, via:"backend", reason}]`，取自 R2 裁决后的 kept 对。
- fair_report_js：渲染 `intent_matches` 时优先用 `intent_matches_backend`；
  没有才走本地 matchIntent 重算（本地换画像 recompute 场景保留）。
- miPairVerdict 同步 R1/R3，保证 recompute 路径与后端同一口径。

### R5 · fair_bridge 原始 jobs 泄漏点隔离（推断岗不得进证据）
- 1314 行 `title_all` 改用 `_clean_jobs`（电科55所 matched_jobs 被推断岗污染已坐实）；
  794/1045/1058/1506 各处逐一核对改隔离。

### R6 · 采集端推荐岗位选项去「校招」字眼
- `ent_tools/js/recommend.js` 兜底池 44 处「（校招）」后缀全部去掉
  （「后端开发工程师（校招）」→「后端开发工程师」）。岗位名本来就该是通用校招写法，
  校招与否由命中时的来源标签说，不由选项名说。

## 补记（同日 23:4x）：轮岗泛岗不硬命中（用户手测第二轮）

用户报：科力普「管理培训生 ↔ 物流专员」被收进「岗位语义命中」，理由写
「大模型判断二者类似工作内容：同属一个职能」。

**根因**：大类闸（is_bare_generic：管培生/储备干部/研究员只问不算）被
`biz_ok` 短路——公司主营含「采购/物流」时（科力普办公一站式采购服务），
bare 分支直接 `kept`，轮岗泛岗变成对口证据。对称的口子在 `ask_jobs`：
业务对口时直接跳过提问。

**修法**（Python/JS 两端同源）：
- 轮岗类（is_rotation_job：管培/培训生/储备干部/储干/校招生）**一律不硬命中**，
  即使 biz_ok 也只转现场问——先轮岗后定岗，岗位名没有「就是干这个」的证据；
- 业务对口时问句升级（hot）：「这家主业就是X所在的方向，大概率会往这个条线
  培养，现场问轮岗后能否定岗到X」；业务无关保持通用问法；
- 带方向的管培生（物流管培生 ↔ 物流专员）与业务对口的定向大类岗
  （供应链公司的「专员」）不误伤，照常命中/按对口处理。

**验证**：新增 5 例单测（共 17 例全过）；parity 3552 对 100% 一致；
规则回归退化 0；_test_match 失败 0；端到端：全库 backend 命中中无方向
轮岗泛岗为 0（江中食粮「设备维修管培生↔设备工程师」为带方向正确命中）。
备份 `_bak_careersafari_20261116/轮岗泛岗不硬命中/`。

## 补记二（同日 23:5x）：软件条线补闸（用户二次点名「软件工程师 ↔ 研发工程师」）

第一轮 ⓪ 闸只拦「剥得出方向核」的岗位（C++研发/自动化/电控硬件），而
「软件」在 DIR_NEUTRAL 中性词表里（防「软件工程师 × 系统工程师」误拆），
剥完方向核为空 → 闸不触发 → 落回无条件 ok。编程条线岗成了最大的漏网面。

**修法**（Python/JS 同源，新增 DEV_SOFTLINE / MI_SOFTLINE 词表）：
- ⓪ 闸条件扩为「方向核非空 **或** 岗位名带软件条线词（软件/程序/编程/编码/
  代码/信息技术）」→ 泛研发意向 × 编程条线岗一律转现场问；
- 意向自己就写了软件条线词（学生勾「软件工程师」）时不触发——软件条线互配
  （软件工程师 × 软件开发工程师）是同条线正常命中；
- JS miMatch 的「字面包含」口子同堵（软件研发工程师 ⊂ 研发工程师 曾绕闸命中）；
- 行为变更：第一轮测试基线「软件研发工程师/软件开发工程师 × 泛研发意向 = ok」
  两条断言按新口径改为 ask——名字带「软件」不是「同样泛」，是编程条线。

**验证**：单测 22 例全过（新增 5 例）；parity 5064 对 100% 一致；规则回归 0；
_test_match 失败 0（另：2 条 FAIL 是用户化学画像 sem 映射缺「环境监测工程师/
配方工程师」，live_map 补判后恢复，非本次回归）；端到端：纯泛研发画像
（只勾「研发工程师」）下全库软件条线 backend 命中 = 0。
